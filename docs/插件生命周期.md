# 插件生命周期

Keymaster 使用 `webloom-framework@0.5.0` 管理插件产品、运行单元、依赖和作用域。
仓库中不再保留另一套通用插件调度器。

## 基本对象

| 对象 | 中文含义 |
| --- | --- |
| Product（产品） | 用户看到并可配置的插件能力 |
| Runtime Unit（运行单元） | 产品在 Window 或 SharedWorker 中的一份实现声明 |
| Instance（实例） | 某运行单元在特定作用域中的一次运行 |
| Capability（能力） | 带编号和版本的受限服务接口 |
| Intent（意图） | 用户希望插件启用或停用的持久状态 |

manifest 必须显式声明运行位置、作用域、依赖、提供的能力和存储用途。静态声明不等于实例
已经成功启动；广播网关页读取实际运行快照。

## 单元可用性

可用 = **插件开着 且 单元已就绪**，两者缺一即不可用。判定递归通过依赖图自然完成，
调用方不自己递归；没有依赖要等就是永远可用，这是判定规则的自然结果，不需要特判。

| 插件 | 单元 | 可用 |
| --- | --- | --- |
| 开 | 已就绪 | 可用 |
| 开 | 未就绪 | 不可用 |
| 关 | 任意 | 不可用 |

因此读一个单元的「已就绪」就等于把该单元这条 AND 整条求过值了：已就绪的含义即
「我插件开着 + 我依赖的全可用 + 我已就绪」。

**状态二值化。** 单元快照状态只有 `ready | failed`，没有 `starting`——收到了也不能用的
状态等于没有。`failed` 表示「现在不可用」，**不**表示「永远不会可用」：依赖变化后必须能
自己变回 `ready`，不允许要求用户再操作一次。

**诊断与状态分离。** 状态字段只回答「能不能用」；为什么不能由 `reasons` 逐条承担。
多依赖可能同时不满足，原因必须逐条列出并支持依赖链下钻，**不允许只报第一个**。

| 字段 | 中文含义 |
| --- | --- |
| `code` | 不可用的稳定代码，程序据此判断、测试据此断言 |
| `dependencyId` | 不可用的依赖：产品 id 或单元 id |
| `text` | 界面直接可用的文案，含翻译 key 与**英文**兜底；中文走 i18n 资源 |
| `dependsOn` | 本单元可用所依赖的全部对象 |
| `state` | `ready` 或 `failed` |
| `reasons` | 失败原因的全部分解；`ready` 时为空 |

`code` 的取值与含义：

| `code` | 中文含义 |
| --- | --- |
| `plugin-disabled` | 本单元所属产品被用户停用 |
| `dependency-disabled` | 声明依赖中的**产品**被停用 |
| `dependency-not-ready` | 声明依赖中的**运行单元**现在不可用 |
| `unit-not-ready` | 本单元自己还没就绪（`starting` 被折叠后由本 code 承担） |
| `storage-root-unavailable` | 中央存储根未就绪 |
| `owner-session-unavailable` | Vault 未解锁或没有 active key |
| `unit-unknown` | 单元未在目录中登记 |

同一个依赖不会被列两次：下钻拿到的原因若只有「它自己还没起来」这一条，就不再额外
补一条「依赖它不可用」——两者是同一句话。子依赖若有自己的原因（产品被停用、它自己的
依赖不满足），则依赖关系与子原因都列出。

### 依赖声明

单元目录的依赖字段合并为一份（`dependsOn`），容纳产品 id 与其它单元 id，统一按
「是否可用」判定；原来的「产品级运行前置条件」不再是独立一层。启动时静态校验依赖图
无环、无未知 id。有任务的单元必须把自己产品写进依赖清单；进了目录的单元必有任务或
服务。

「A 需要 B 就绪」这个事实必须有声明位置。依赖只写在调用代码的一行 `await` 里，等于没有
声明：谁调、调在哪、B 何时会好全靠调用方现场推断，推断错一次就是一个竞态。

### 单一实现

可用性判定只有一份实现（`apps/web/src/coordinator/workerUnitAvailability.ts`），同一份
规则回答三个问题：

| 求值 | 回答的问题 | 使用方 |
| --- | --- | --- |
| 启动前置条件 | 调度器现在能不能起这个单元 | 框架门 `runtimeUnitAvailability` |
| 构造前置条件 | 现在能不能把运行对象建出来 | `ensure*Runtime()` |
| 完整可用性 | 现在能不能用 | 公开快照投影、各能力自己的依赖门 |

框架门与 Worker 本地判定**不允许各判一次**；`ensure*` 里的「reconcile 一下然后祈祷它
已就绪」兜底一律删除，测试逃生口一律取消。**不保留双轨、不做分阶段灰度、不留迁移中间
态提交。** 统一比渐进重要：两条路并存时，「哪条路是对的」本身就是一个需要反复判断的
问题。

构造前置条件不含声明依赖，是因为依赖是**使用**前置条件而不是构造前置条件：依赖暂时不可
用时运行对象仍要能建起来，否则依赖一掉线，连「把用户开关关掉」这种必须永远可用的操作
都做不到。

### 触发方式

Worker 进程内提供可用性订阅，签名 `onChange(handler): () => void`，返回取消函数。
`ready` 与 `failed` **双向都触发**，不是只在变好时通知。消费方订阅后重判自身状态，重判
必须幂等。**任何环节不得引入轮询、等待休眠或超时猜测。** 抖动只会带来连续几次幂等重判。

页面侧沿用既有的 `worker.units` 推式通道与其单调修订号，不新增轮询。

**名单里看得到什么。** 单元快照会包含所有已登记的单元，包括正在启动的和被依赖挡住
的：它们会如实报 `failed` 并给出 `reasons`。只有一种情况不进名单——**用户主动关掉了这个
单元自己的产品**，那是用户的选择而不是故障。判断只看「本单元自己的产品是否被关」，不
要求原因列表全是 `plugin-disabled`：目录里单元通常把自己的产品也写进了 `dependsOn`，
关掉产品会同时产生一条 `dependency-disabled`。

**实例标识允许缺省。** 单元标识用来分辨「哪一次运行」，而从未启动过的单元没有哪一次运行
可分辨——框架在「能不能启动」被否时就返回了，还没走到分配标识那步。因此快照会省略这个
字段而不是编造占位值，WebLoom 自身的状态投影也是这么做的。消费方按实例比对前必须判空。

### 单一就绪来源

「单元自身是否已就绪」**只有一个来源：运行态注册表**。`activate` / `ready` / `fail` /
`stop` 四条边沿都会推 `onChange`，因此只读注册表既不缺边沿，也不需要第二把尺子。

判定里**不允许**再读 WebLoom Host 的单元状态来判就绪。Host 只负责调度与枚举单元。要读它
就必须同时订阅它，而 Host 状态没有接进可用性订阅，于是会出现「判定翻成 `ready` 却没人
被叫醒重判」的静默卡死：卖方永久停在 `waiting-dependency`，无报错、无日志，只能手动重切
开关。Host 自身的健康度由别处 fail closed——`coordinatorRuntimeUnitSnapshots()` 在 app
`failed`/`disposed` 时返回空快照，`reconcileCoordinatorRuntime()` 无 app 时空转。

去掉 Host 那一侧不丢信息，因为顺序单向：`coordinatorRuntimePlugins` 的 setup 钩子对全部
领域单元都先 activate 再 ready，Host 只在 setup resolve 之后才置 enabled，注册表 ready
严格早于 Host enabled。

### 验收命令

```bash
# 1. 不可用必须表达为 waiting-dependency，不得回退成永久错误文案。
rg -n "unit is not ready" apps/web/src/keymasterSessionCoordinator.worker.ts
# 2. 门外逃生口已清除，源码 0 命中。必须限定在源码目录内：把检索串写进本文档
#    会让门禁匹配到它自己，与门禁 1 是同一个自指陷阱。
rg -n --glob '*.ts' "testMsfileRuntimeRecoveryAllowed" apps packages
```

门禁 1 的检索串**必须是 `unit is not ready`**，不能是 `is not ready`：后者会命中 6 处与本
判定无关的既有文案（Test Coordinator garbage storage、Channel runtime、Owner storage、
Test platform storage），门禁永远不可能绿，失去意义。

「禁止轮询」不作为自动门禁，改为**人工审查项**。`setInterval` 单独作为门禁太弱：`while` +
`await` 和递归 `setTimeout` 都能绕过，而本文件里本来就存在合法的有界观察/重试循环（快照
新鲜度收敛、广播结果确认、快照重试），把它们一并禁掉会误伤。审查时看的是：可用性判定与
订阅回调内**没有**定时器、休眠或轮询——`coordinatorWorkerUnitRegistry.onChange` 与
`watchMsfileSellerDependency` 两处应当干净。

### 卖方开关

用户开关与实际可接单状态是**两个正交维度**，不合并。

- 开关关 → 短路，不评估可用性，不残留索引与运行时。
- 开关开 → 评估可用性。不可用时如实报不可用（`waiting-dependency`）并订阅变化，
  **不拆解**、**不要求用户重切**。
- 「依赖未就绪」不得再由永久错误状态表达。现有「自建索引中」与「协议端口未就绪」语义
  都不同，需要独立的一档状态，避免界面提示错位。

## 撤权顺序

锁定、切 Key、切桶或停用插件时统一执行：

```text
阻止新请求 → 推进 epoch/generation → 撤销代理与租约
→ 等待有界的在途操作 → 释放网络、监听和界面注册
```

`epoch` 表示会话代际，`generation` 表示桶、Provider 或配置代际。任何最终存储、签名、
广播或付费 I/O 都要再次核对这些值。清理失败可以被报告，但不能恢复旧授权。

## 跨页面唯一运行

WebLoom 0.5.0 负责 SharedWorker Host、物理 peer 生命周期和 typed capability
撤权，但不提供跨物理 Worker 的 Runtime Lock。Keymaster 在 Worker 初始化、公开
Coordinator capability 和进入 final-I/O 前，必须取得自己的 origin 级 Web Lock：
`keymaster.coordinator.authority:v1`。这把锁从 Worker 启动保持到退场，所以旧/新
构建使用不同 Worker URL 时也只能有一个物理 Worker 成为 authority；锁冲突或原生
Web Locks API 不可用都必须 fail closed。

peer/session、lease、epoch/generation 继续负责页面会话、撤权、排空和迟到结果；
它们不是跨 Worker authority 的替代品。

页面端的 `keymaster.page-presence:*` Web Lock 只用于尽力判断“是否仍有其它页面在场”，
帮助刷新后的唯一页面回到锁定态；它不能代替 Worker authority lock、会话撤权或存储 CAS。
页面 presence 缺失时可以保持兼容行为，但 Coordinator authority lock 缺失时不能启动。

## 升级和未知结果

- 从旧版本升级时，必须先确认旧页面和 Worker 已排空退出，再启用新版本；新包不能抢占
  仍持有 `keymaster.coordinator.authority:v1` 的旧 Worker。
- 冷切换和回退都必须经过 authority Web Lock、final-I/O lease、traffic drain 以及现场交接证据；
  WebLoom 的 peer 事件只报告物理连接变化，不能替 Keymaster 选择 owner。
- Worker 崩溃后远端请求可能已经成功；广播、上传、订阅和支付必须按领域记录对账，不能
  因为新的 Worker 启动就自动重放。

## 发布门禁

本地生命周期、registry 安装和 Chromium 主链已有自动化入口。正式发布还必须使用
目标 Build ID 验证外部 AppView、不可逆 I/O、Coordinator 恢复和旧 Worker 退出证据：

```bash
pnpm test:e2e:lifecycle
pnpm verify:lifecycle-release
```

缺少外部环境时应保持“未执行/阻断”，不能用本地测试替代生产验收。

发布时先运行 `pnpm prepare:lifecycle-evidence` 生成证据骨架，再填写
[部署交接模板](./集成测试/资源配置模板/部署交接.json.example)，不要另建施工单。
