# 存储桶、Key 与会话设计 V1

> 更新：2026-09-14
>
> 状态：V1 代码实现与自动化验收收口中；真实浏览器多页证据需按验收命令补充。

## 1. 总体边界

存储桶是 Keymaster 的最外层数据边界，一个桶可以包含多把 Key。桶配置、桶内 Key、中央系统数据和 Owner 业务数据都属于当前桶；设备发现信息属于浏览器公共存储；定时器、连接、锁和任务运行状态属于内存。

V1 只支持两类桶 Provider：

- Local：通过受控的浏览器 `localStorage` 保存桶对象；页面桥接不暴露给插件。
- S3：通过受控的 S3 Provider 访问对象桶；凭据只在 Coordinator 会话内存中存在。

插件只能取得 Host 绑定的 Borrowed Store 或文件服务。插件不接触 Provider、S3 SDK、凭据、桶世代或物理路径。

## 2. 桶目录与公共存储

浏览器公共存储只保存最小启动信息：桶 ID、显示名称、后端类型、配置版本、选中桶和加密连接记录，以及明确允许的语言、主题和窗口握手信息。S3 的连接记录使用桶密码保护，不包含 Key 列表或业务数据。

当前桶内使用固定的系统和业务命名空间：

```text
.keymaster/hold/v1
.keymaster/system/<module>/<purpose>/
<ownerPublicKeyHex>/.keymaster/modules/<module>/<purpose>/
```

桶 Provider 只看到抽象桶内的对象。系统目录、Owner 目录、Hold 和 K-V 引擎路径由 platform-storage 生成；插件只提交已绑定接口允许的业务 key 或相对文件路径。

## 3. 桶密码

密码属于桶，不属于单独的 Key。桶配置密文和 Hold 密文使用同一桶密码上下文保护。密码只在一次测试、保存、解锁、切换、导出或改密操作期间存在于内存，操作结束即释放；不得写入目录、日志、事件或长期运行状态。

解锁当前桶的基本流程：

```text
输入桶密码
  → 解密并校验桶连接记录
  → Coordinator 创建唯一 bucketProvider
  → 读取并认证当前桶 Hold
  → 从 Hold 恢复公开 Key 索引
  → 建立当前 Key 会话
  → 释放密码和临时解密上下文
```

同桶切换 Key 必须再次输入桶密码。跨桶切换必须先验证目标桶并暂存完整绑定，所有中央句柄和运行时绑定在成功发布后一起替换；失败时保留当前桶或进入明确的 fail-closed 状态。

## 4. Hold 与 Key 唯一真相

`.keymaster/hold/v1` 是私钥密文唯一位置。普通系统 K-V 只保存：

- `vault/auth-metadata`：KDF 参数和密码 verifier；
- `vault/key-index`：公钥、标签、地址、网络和能力；
- `vault/key-lifecycle-journals`：Add/Delete 共用的公开 Key 身份、事务阶段和 Hold Head 关联。

生成、导入、备份导入、导出、删除、改密和解锁全部通过 Hold adapter 完成。发布顺序是“读取并认证当前 Hold → 构造完整下一代 Hold → CAS 发布 Hold → 更新可重建的公开索引”。索引写入失败时，下次启动从 Hold 重建，不复制私钥密文到普通 K-V。

V1 不启用 Passkey 私钥解锁。后续若增加 Passkey，只能包装 Hold 的解锁能力，不能再保存第二份私钥密文。

## 5. Coordinator 系统存储

Coordinator 在当前桶绑定时统一打开并负责关闭以下句柄：

```text
Snapshot:
  coordinator/selection
  coordinator/settings
  coordinator/plugin-intent
  storage/profile-salt

K-V:
  storage/multipart-uploads
  protocol/durable-policy
  protocol/sessions
  protocol/command-history
  vault/auth-metadata
  vault/key-index
  vault/key-lifecycle-journals
```

插件只能获得已经绑定的 Borrowed Store；插件 Repository 的 `close()` 只使 Repository 自身失效，不关闭 Host 负责的底层句柄。

`coordinator/plugin-intent` 是插件启停状态的唯一持久化来源。写入顺序为：成功发布 snapshot → 更新 Runtime 内存投影 → 启动或停止插件。snapshot 写入失败时不能改变内存启停真相，也不能先启动插件再补写。

## 6. Storage Runtime

Storage Runtime 只管理 Coordinator 注入的当前 `bucketProvider`，不保存 Provider 选择、切换记录或连接配置。Provider 的创建、认证、切桶和配置改动属于 Coordinator 的桶目录/管理流程。

Runtime 内存可以保存：

- 当前 Provider 对象及其脱敏摘要；
- 请求取消控制器、分页 cursor、上传锁；
- multipart 远端 upload ID 的当前会话映射；
- 条件写能力探测结果和生命周期栅栏。

桶级 K-V 只保存 multipart 恢复元数据：上传身份、对象 key、已完成 part、大小、创建/过期时间、桶和会话世代，以及经当前会话密钥封装的远端 upload ID。不得保存文件内容、凭据、密码或连接对象。

## 7. 失败和生命周期

- 真实读写失败就地返回稳定错误，不创建本地业务副本。
- 锁定、切桶、Owner 删除或桶世代变化会立即使旧请求、句柄和租约失效。
- Provider 调用有边界和取消栅栏；迟到结果不能重新激活旧 Owner 或旧桶。
- 初始化、切桶和改密采用先暂存、再 CAS 发布的顺序；中途失败不得留下半绑定的当前桶。
- Local 容量、同步写入和 S3 条件写能力都作为真实限制处理。

## 8. 安全检查

系统目录禁止出现私钥、Hold 密文或可恢复私钥的副本。所有模块声明必须由中央注册表精确匹配 `moduleId + purposeId + scope + authority + model + schemaVersion`。第三方 App 的模块身份只能从已验证发布者身份和 App ID 派生。

平台层负责物理路径、Provider 条件写、ETag、桶世代和 GC；业务插件只看到受限接口，不能通过参数扩大到其他模块、Owner 或桶。
