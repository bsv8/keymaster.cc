# Keymaster 统一存储结构

## 1. 核心模型

Keymaster 先选择或导入一个“抽象桶”，然后才能读取、选择、导入或新建 Key。
抽象桶的 Provider 可以是 OPFS 或 S3，上层不得根据 Provider 类型分叉业务逻辑。

一个桶内可以容纳多把 Key：

```text
Abstract Bucket（OPFS 或 S3）
├─ keys/                         # 平台全局区，只有平台 App/API 可访问
│  ├─ meta
│  └─ <publicKeyHex>
├─ <publicKeyHex-001>/           # Key/owner 受限区
│  ├─ UTXOS/                   # 系统 App 自声明的命名空间
│  ├─ Contacts/                # 系统 App 自声明的命名空间
│  ├─ <third-party-app-uuid>/  # 三方 App 命名空间
│  └─ <another-app-uuid>/
└─ <publicKeyHex-002>/
   ├─ UTXOS/
   ├─ Contacts/
   └─ <third-party-app-uuid>/
```

S3 Object Key 和 OPFS 相对路径均不使用开头的 `/`。文档中的
`/keys` 只是逻辑根目录的展示形式。

## 2. 权限边界

### 2.1 平台级

只有 Keymaster 平台 App 和平台内部 API 可以申请桶级全局权限。典型用途：

- 访问 `keys/`，保存 Vault meta、加密后的私钥文档和 Key 列表；
- 管理抽象桶本身的 schema、健康状态和压缩信息；
- 在删除 Key 时统一删除该 `publicKeyHex/` 受限区。

`meta.kind === "core"` 或“Keymaster 自带”不等于拥有全局存储权限。
全局权限必须由平台装配层显式授予，不向 Connect 或普通插件暴露。

### 2.2 Key/owner 级

系统 App 和三方 App 都只能获得预绑定的受限句柄：

```text
bucketId + ownerPublicKeyHex + applicationStorageId
```

句柄不允许调用者传入或替换 `bucketId`、`ownerPublicKeyHex` 或
`applicationStorageId`。切换 active Key 后，旧 Key 句柄立即失效。

系统 App 也必须在 manifest 中自声明存储，例如：

```ts
storage: {
  scope: "key",
  applicationStorageId: "Contacts"
}
```

`UTXOS` 和 `Contacts` 只是两个系统 App 的稳定命名空间，不是平台特权。
运行时必须拒绝重复声明、保留名和越界路径。

三方 App 的 `applicationStorageId` 是由已验证 App Identity 派生的稳定
UUID，同时绑定 Publisher 和 App ID。Caller 不能自报 UUID。

## 3. K-V 契约

业务数据不得直接使用 IndexedDB、localStorage、OPFS 或 S3 SDK。
只能使用 Keymaster 发放的 K-V 句柄：

```ts
interface KeyValueStore {
  get<T>(key: string): Promise<KvEntry<T> | undefined>;
  list(input?: KvListInput): Promise<KvListResult>;
  put<T>(key: string, value: T, condition?: KvWriteCondition): Promise<KvEntryMeta>;
  delete(key: string, condition?: KvWriteCondition): Promise<void>;
  commit(input: KvCommitInput): Promise<KvCommitResult>;
}
```

| 字段 | 中文含义 |
|---|---|
| `key` | App 命名空间内的相对 K-V 键，不是物理 S3 Key |
| `value` | JSON 或二进制值 |
| `revision` | 命名空间中由平台分配的单调版本 |
| `ifRevision` | 仅当当前版本一致时才写入，用于防止覆盖 |
| `partition` | 一组需要原子提交的 K-V 键所属分区 |
| `cursor` | 只由平台解析的分页位置，不得夹带物理路径 |

`commit` 在同一 `partition` 内原子发布多个 put/delete。P2PKH 的本地交易、
input claims 和 outputs 必须位于同一分区，不得用多次普通 `put` 模拟事务。

Provider 内部可使用保留的 `.keymaster/` 对象实现 revision、commit head、
不可变更日志和压缩。这些对象不是 App 可见 K-V，App 不得列出或修改。

## 4. Provider 约束

### 4.1 OPFS

- 使用 origin private file system 作为抽象桶；
- 在 SharedWorker/Worker 内持有唯一 writer；
- 写入使用临时文件、flush/close 和 head 替换；
- 启动时检查 API、可写性、持久化授权与 quota；
- OPFS 不可用时不得自动降级到 IndexedDB。

### 4.2 S3

- AWS S3、Cloudflare R2 和 S3-compatible 都通过同一 Provider 契约；
- 系统 K-V 必须具备原生条件写能力（`If-Match` / `If-None-Match`）；
- 只有 best-effort `HEAD -> PUT` 的 S3 Provider 不得被激活为 Keymaster 系统桶；
- commit 先写不可变更对象，再使用 ETag 条件更新分区 head；
- 任何冲突返回稳定的 `storage_conflict`，不静默覆盖远端数据。

## 5. 启动顺序

```text
1. 加载存储启动信息
2. 选择或导入抽象桶（OPFS / S3）
3. 全局探测桶的可读、可写、条件写和 schema
4. 通过平台 API 读取 keys/
5. 选择、导入或新建 Key
6. 建立 <publicKeyHex>/ 受限上下文
7. 启动系统 App
8. 允许三方 App 建立 Connect Session
```

存储未选择、不可用或需要重新认证时，Vault/Keys、系统 App 和三方 App
均不得启动。不使用本地旧数据或另一 Provider 自动兜底。

## 6. S3 冷启动边界

S3 连接凭据不能再由 Vault 加密：读取远端 `keys/` 之前必须先能连接 S3，
而 Vault 又位于 `keys/` 中。

因此存储连接器是唯一 bootstrap 边界：

- S3 存储 Profile 使用独立的存储密码加密，不使用任何 Key 的私钥或 Vault key；
- 导出/导入的 Profile 包含 Provider、Bucket 位置和加密凭据；
- 本机只允许保存“选中的 Profile ID + 加密 Profile envelope”，不保存业务数据；
- 存储密码只用来打开 S3 连接器，不加密私钥；
- 如果不允许本机保存加密 envelope，则每次冷启动必须重新导入 Profile；
- 除该连接器和首屏语言/主题偏好外，IndexedDB/localStorage 不得承担持久化真值。

## 7. 可用性与恢复探测

存储健康状态是全局真值：

```ts
type StorageRuntimeStatus =
  | "unselected"       // 未选择桶
  | "authentication"   // 需要导入/解锁存储 Profile
  | "checking"         // 正在探测
  | "ready"            // 可读、可写且满足事务条件
  | "degraded"         // 已有业务数据，但 Provider 暂时失联
  | "incompatible";    // schema/条件写能力不符合要求
```

- 首次连接必须做 read/write/delete 和条件写探测；
- `ready` 后由 Coordinator 执行单一全局健康任务，页面不自建 timer；
- 请求遇到 network/CORS/auth/provider 错误会立即推进全局状态；
- 网络恢复、页面重新可见或用户手动点击时可立即重试；
- 自动恢复使用有上限的指数退避和 jitter，同一时刻只有一个 probe；
- 在 `degraded` 期间所有需要真实存储的写操作 fail closed，不积累隐式本地写队列；
- 恢复到 `ready` 后统一 invalidation 相关 resource，再恢复后台任务。

## 8. 硬切换原则

本次不考虑旧数据迁移：

- 不读取旧 IndexedDB/localStorage 业务真值；
- 不写双份，不提供 fallback，不保留 compatibility adapter；
- 旧 DB 可由独立、明确的用户清理操作删除，新系统启动不自动删除；
- 测试必须搜索并拒绝生产路径新增 `indexedDB.open` 或业务 `localStorage` 访问。

## 9. 代码结构与命名

本次不在旧 `plugin-storage`、`storageDb`、`KeyScopedStorage` 等名字上叠加新语义。
目录和符号必须直接表达所属层级和权限：

- `platform-storage`：Storage 平台，包含抽象桶、K-V 引擎、权限句柄、启动与健康管理；
- `bucket-providers/opfs` 和 `bucket-providers/s3`：只实现物理桶操作；
- `kv-engine`：只实现 partition、commit、revision、snapshot 和 GC；
- `storage-access/platform-root`：只实现平台全局权限；
- `storage-access/owner-app`：只实现 bucket/owner/App 受限权限；
- 业务插件使用 `storage/*Repository.ts`，不再使用 `*Db.ts` 命名。

名字必须体现权限：

| 新名字 | 准确含义 |
|---|---|
| `BucketObjectStore` | OPFS/S3 物理对象层，不包含 App 权限 |
| `PartitionedKvEngine` | 在抽象桶上提供原子 K-V commit |
| `PlatformRootStore` | 平台全局句柄 |
| `OwnerAppStore` | 已绑定 owner public key 和 App 的受限句柄 |
| `StorageRuntimeController` | 管理当前桶、generation 和生命周期 |
| `StorageHealthController` | 管理全局探测、退避与恢复 |

不保留旧名字的 type alias、wrapper、barrel re-export 或 compatibility 目录。
