# Keymaster 中央系统存储 V1

本文是 V1 的现行存储规范。所有存储消费者先在中央注册表登记模块用途，再由 Host/Coordinator 绑定到当前桶或当前 Owner。V1 不保留第二套持久化真相，也不把运行时对象写成系统数据。

## 1. 中央声明注册表

每一项声明必须同时包含稳定的 `moduleId`、`purposeId`、`scope`、`authority`、`model` 和 `schemaVersion`：

```ts
{
  moduleId: "contacts",
  purposeId: "address-book",
  scope: "owner",
  authority: "built-in-module",
  model: "kv",
  schemaVersion: 1
}
```

注册表位于 `packages/contracts/src/storage/systemStorageDeclarations.ts`，是中央系统和内置模块声明的唯一来源。平台声明如下：

| module / purpose | scope | authority | model |
|---|---|---|---|
| `coordinator / selection` | bucket | platform-only | snapshot |
| `coordinator / settings` | bucket | platform-only | snapshot |
| `coordinator / plugin-intent` | bucket | platform-only | snapshot |
| `storage / profile-salt` | bucket | platform-only | snapshot |
| `storage / multipart-uploads` | bucket | platform-only | kv |
| `protocol / durable-policy` | bucket | platform-only | kv |
| `protocol / sessions` | bucket | platform-only | kv |
| `protocol / command-history` | bucket | platform-only | kv |
| `vault / auth-metadata` | bucket | platform-only | kv |
| `vault / key-index` | bucket | platform-only | kv |
| `vault / key-lifecycle-journals` | bucket | platform-only | kv |

普通插件的设置、历史和状态也必须引用同一注册表中的声明。第三方 App 的 Owner 模块身份由已验证的 `(publisherPublicKeyHex, appId)` 派生，Connect 请求不能自报模块、Owner、桶或物理路径。

## 2. 数据归属

| 数据类别 | 位置 | 说明 |
|---|---|---|
| 设备发现信息 | 浏览器公共存储 | 加密桶目录、当前桶选择，以及明确允许的语言/主题偏好 |
| 桶级系统配置 | 当前桶 | 四个固定 snapshot；插件意图只有一个持久化来源 |
| Owner 业务数据 | 当前桶的 Owner namespace | 联系人、消息、UTXO、Token、文件等按模块/用途隔离 |
| 安全控制数据 | 当前桶的 Vault 系统声明 | 认证元数据、公开 Key 索引、Add/Delete 生命周期事务日志 |
| 私钥密文 | 当前桶 `.keymaster/hold/v1` | Hold 完整提交快照，是私钥密文唯一真相 |
| multipart 恢复数据 | 当前桶 `storage/multipart-uploads` | 只保存恢复所需的上传元数据和封装后的远端 upload ID |
| 运行时状态 | Coordinator/插件内存 | timer、lease、锁、连接、当前任务、请求、临时 Key 材料 |
| 存储引擎对象 | 当前桶内部 | full head、唯一 value 对象和固定 snapshot 对象 |

`.keymaster/system/**` 禁止出现私钥字节、KeyHold 文档、Hold 密文或能恢复私钥的副本。密码和解密后的 S3 凭据只存在于本次操作或当前桶会话内存。

## 3. 物理布局

Provider 只处理当前抽象桶中的对象；业务插件不会看到下面的物理路径。

```text
抽象桶
├─ .keymaster/schema
├─ .keymaster/owners/<ownerPublicKeyHex>
├─ .keymaster/hold/v1
├─ .keymaster/system/coordinator/selection/current
├─ .keymaster/system/coordinator/settings/current
├─ .keymaster/system/coordinator/plugin-intent/current
├─ .keymaster/system/storage/profile-salt/current
├─ .keymaster/system/storage/multipart-uploads/.keymaster/heads/<partition>
├─ .keymaster/system/storage/multipart-uploads/.keymaster/values/<valueId>
├─ .keymaster/system/protocol/<purpose>/.keymaster/heads/<partition>
├─ .keymaster/system/protocol/<purpose>/.keymaster/values/<valueId>
├─ .keymaster/system/vault/<purpose>/.keymaster/heads/<partition>
├─ .keymaster/system/vault/<purpose>/.keymaster/values/<valueId>
└─ <ownerPublicKeyHex>/.keymaster/modules/<moduleId>/<purposeId>/
   ├─ .keymaster/heads/<partition>
   └─ .keymaster/values/<valueId>
```

系统 snapshot 是固定的单对象路径，不接受调用方传入 partition、key 或物理路径。Owner 文件接口只接受已绑定 namespace 内的相对路径，并拒绝绝对路径、父目录、反斜杠、空段、NUL 和保留系统段。

## 4. Snapshot 模型

固定 snapshot 使用严格 envelope：

```ts
{
  format: "keymaster.storage.snapshot",
  version: 1,
  declaration: { moduleId, purposeId, scope, authority, model, schemaVersion },
  revision: 1,
  value: {}
}
```

读取时校验 envelope、完整声明和 payload；首次写入使用不存在条件，后续写入使用上一版本的 CAS 条件。相同语义值不产生 Provider 写入，也不增加 revision。冲突或损坏均 fail closed。

Coordinator 只持久化四个独立 snapshot：当前 Key 选择、调度/P2PKH 设置、插件启停意图和 profile salt。插件启停写入顺序是“成功发布 plugin-intent → 更新内存投影 → 启停插件”；持久化失败时内存真相不改变。

## 5. K-V full-head 模型

每个 partition 只有一个完整可变 head：

```ts
{
  format: "keymaster.kv-head",
  version: 1,
  partition: "records",
  revision: 7,
  committedAt: 0,
  entries: [
    { key: "record/a", valueId: "value-42", valueHash: "<integrity>", updatedAt: 0 }
  ]
}
```

写入先确保新 value 对象存在，再 CAS 发布完整 head。多个键在同一个新 head 中原子可见；无变化的写入不会增加 revision。`valueId` 是唯一对象身份，`valueHash` 只用于完整性校验，不作为对象路径。

V1 的 K-V 只有 `heads/` 和 `values/` 两类对象，不产生不可变提交历史对象。普通写入不调用 Provider `list()`，也不同步等待 GC。

## 6. 生命周期与句柄

Coordinator 在绑定当前桶时统一打开全部中央 snapshot 和平台 K-V：

```text
Snapshots: coordinator/selection, coordinator/settings,
           coordinator/plugin-intent, storage/profile-salt
Platform K-V: storage/multipart-uploads,
              protocol/durable-policy, protocol/sessions,
              protocol/command-history, vault/auth-metadata,
              vault/key-index, vault/key-lifecycle-journals
```

这些句柄由 Coordinator 关闭。插件拿到的是 Host 绑定的 Borrowed Store；插件 Repository 的 `close()` 只使自身失效，不关闭底层句柄。切桶、锁定、初始化失败和 Owner 生命周期变化会使旧 generation 句柄立即失效。

Hold 的生成、导入、导出、删除、改密和解锁都经过 Hold adapter。公开 key-index 可由 Hold 重建；index 写入失败不会产生第二份私钥密文真相。

## 7. GC 约束

Coordinator 低频按注册表枚举桶级 K-V 和当前授权的 Owner K-V，清理 crash orphan。GC 以当前 head 的可见时间保护仍被旧 reader 使用的 value；Local 没有 Provider 修改时间时使用 head 的 `committedAt`，没有 head 的孤儿使用 value 对象时间。删除前再次确认对象不可达。

测试必须覆盖旧 reader、新 head、grace 期、grace 后删除、写入期间 `listCalls === 0`，以及没有长期打开句柄的 namespace。

## 8. 公共存储白名单

浏览器公共存储只负责设备发现和本机桶 Provider 所需的最小数据：加密桶目录/连接记录、语言、主题和窗口握手信息。S3 凭据、Key 目录、业务数据和 Hold 密文不写入公共存储；业务插件也不能直接使用浏览器存储、S3 SDK 或 Provider。
