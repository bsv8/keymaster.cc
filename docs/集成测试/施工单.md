# Keymaster 全覆盖集成测试施工单

## 1. 施工目标

建设一套面向检查者阅读、能够持续扩展并覆盖 Keymaster 全部业务能力的浏览器集成测试体系。

测试代码首先要说明真实用户在完成什么业务、为什么要完成、什么结果代表成功；同时必须继续验证实现这些业务所依赖的技术事实，包括但不限于存储、协议、Worker 生命周期、并发、权限撤销、失败恢复、真实 testnet、真实 S3 和真实远端服务。

本施工单不把 `docs/集成测试/初步设计.md` 中列出的初始化、菜单、聊天、通讯录和 testnet 转账视为完整范围。该文件只是说明“一个前置过程可以被多个后续场景复用”的示例。

最终完成条件是：每一项正式业务能力、关键业务状态、重要失败路径和外部系统边界，都能从覆盖矩阵追踪到负责它的 Journey 或技术 Gate，并有与测试层级相符的执行证据。

## 2. 已冻结的需求裁定

### 2.1 测试写给检查者看

1. Journey 名称、文件头说明、`test.step` 名称和关键断言注释必须使用中文业务语境。
2. 业务注释必须回答：
   - 谁在使用这项能力；
   - 用户开始时处于什么状态；
   - 用户要完成什么事情；
   - 为什么这个结果对用户成立；
   - 失败会给用户造成什么影响；
   - 测试产生了什么外部影响，结束后如何收尾。
3. 不写“点击按钮”“等待元素出现”这类逐行翻译代码的无效注释。
4. 技术名称、API、协议字段和类型名允许保留英文，但第一次出现时必须用中文说明其业务含义。
5. “注释使用业务语境”不等于只测试页面文案或顺利路径。技术断言不得因此减少、弱化或改成表面 UI 检查。

### 2.2 复用的是过程，不是互相依赖的测试

采用四层结构：

```text
Journey（业务旅程，一个可独立报告的 Playwright test）
    ↓ 调用
Flow（可复用业务过程）
    ↓ 调用
Driver（页面、协议和浏览器技术操作）
    ↓ 申请
Resource（S3、testnet 资金、SatSubscription 等外部资源）
```

要求：

1. Flow 是普通异步函数，不在内部注册 `test()`。
2. Journey 是最终测试和报告单位，可以组合任意多个 Flow。
3. 一个 Journey 内，初始化、充值等共同前置过程只执行一次。
4. 独立 Journey 默认拥有独立业务状态，可以单独运行、重试和定位失败。
5. 不允许通过“前一个测试必须成功，后一个测试才能运行”的隐式顺序实现复用。
6. 确实需要共享一个不可重复资源的检查必须组合为同一个 Journey，或由显式 Resource 生命周期管理，不能依赖普通 `beforeAll` 侥幸保持状态。

### 2.3 全覆盖的定义

本施工单中的“全覆盖”是需求与风险覆盖，不是单独以代码行覆盖率衡量。

至少覆盖以下四个维度：

1. 用户可见业务：正式菜单、页面、操作、结果和跨业务组合。
2. 业务状态：未初始化、已初始化、锁定、解锁、刷新恢复、重启恢复、Key/桶切换、多页面等。
3. 失败恢复：输入错误、权限不足、余额不足、网络失败、结果未知、并发冲突、远端不可用和清理失败等。
4. 外部边界：真实浏览器、生产构建、testnet、S3、SatSubscription、P2P、外部 App 和目标部署等。

不要求对所有维度做无意义的笛卡尔积。覆盖矩阵必须证明每项正式能力有人负责，每个高风险边界至少存在一个成功用例和一个有业务意义的失败/恢复用例。

## 3. 测试分层与证据边界

| 层级 | 中文含义 | 默认运行时机 | 可以证明什么 |
| --- | --- | --- | --- |
| `local-integration` | 本地浏览器集成测试 | 每个 PR | 生产构建在真实浏览器中的业务组合、生命周期和本地确定性失败 |
| `real-resource` | 真实资源集成测试 | 定时任务或人工触发 | 真实 testnet、S3、SatSubscription、P2P 等边界可用 |
| `deployment-acceptance` | 目标部署验收 | 发布前后 | 指定不可变 Build ID 的公开部署完成真实业务链 |

约束：

1. Mock、内存 Provider 或 Node `MessageChannel` 通过，不得宣称真实浏览器或真实 Worker 已通过。
2. 本地 preview 通过，不得宣称目标部署已通过。
3. 真实 testnet 通过，不得自动宣称 mainnet 或公开生产服务已通过。
4. 每个 Journey 在覆盖矩阵中必须声明自己的层级；报告必须按层级分别汇总。
5. 未执行的层级必须明确报告“未执行”，不得用较低层级结果替代。

## 5. 覆盖矩阵

### 5.1 真值来源

实施时必须盘点并交叉核对：

1. `apps/web/src/pluginCatalog.ts` 中装配的正式插件；
2. 各插件 manifest 注册的业务域、feature、route、settings、command 和公开能力；
3. `packages/contracts` 中对用户或外部 App 开放的正式契约；
4. 初始化、存储、Vault、Coordinator、Worker 和插件生命周期；
5. 现有 E2E spec 已经验证的技术边界（迁移后统一位于 `e2e/integration/`）；
6. 正式设计文档、施工单和已冻结验收条目；
7. S3、testnet、SatSubscription、P2P 和目标部署等外部依赖。

不能只扫描路由生成覆盖清单。没有页面的后台同步、权限撤销、恢复和协议行为同样属于正式覆盖范围。

### 5.2 矩阵字段

`覆盖矩阵.yaml` 至少包含以下字段，并在模板中保留中文说明：

| 字段 | 中文含义 |
| --- | --- |
| `requirement_id` | 稳定的业务或技术需求编号 |
| `business_domain` | 所属业务域 |
| `user_role` | 谁在使用这项能力 |
| `user_goal` | 用户最终想完成什么 |
| `starting_state` | 场景开始时的业务状态 |
| `expected_result` | 用户可以观察到的成功结果 |
| `technical_truths` | 为证明业务成立必须验证的技术事实 |
| `failure_paths` | 必须覆盖的失败和恢复路径 |
| `resource_profile` | 依赖的真实资源 |
| `cleanup_policy` | 场景产生状态后的清理/保留规则 |
| `gate_level` | 本地、真实资源或部署验收层级 |
| `scenario_ids` | 负责验证它的 Journey/Gate 编号 |
| `evidence` | 最近一次有效证据或明确的未执行状态 |
| `status` | 已覆盖、部分覆盖、阻断或未覆盖 |

### 5.3 自动一致性门禁

新增检查脚本，至少阻断以下情况：

1. 正式业务 feature、route 或公开协议已经存在，但覆盖矩阵没有登记。
2. 覆盖矩阵引用了不存在的 Journey/Gate。
3. Journey 声明的需求编号在覆盖矩阵中不存在。
4. 一个需求被标记为“已覆盖”，但没有任何可执行场景。
5. 真实资源需求只有本地 Mock 证据，却被标记为真实验收通过。
6. 生成的 `覆盖矩阵.md` 与 YAML 真值不一致。

## 6. Journey 与注释规范

### 6.1 Journey 文件头模板

每个 Journey 必须使用如下结构；允许按业务需要增加内容，不允许删除核心字段：

```ts
/**
 * 业务目标：
 * 新用户完成首次初始化后，可以保存联系人并向对方发送第一条消息。
 *
 * 用户价值：
 * 证明刚安装 Keymaster 的用户可以建立自己的身份，并开始一段可恢复的通信。
 *
 * 开始状态：
 * - 浏览器中没有 Keymaster 历史数据；
 * - 对端测试身份已经可用。
 *
 * 成功标准：
 * - 初始化在本场景中只发生一次；
 * - 刷新页面后联系人仍然存在；
 * - 已发送消息能够重新读取，并且归属正确联系人。
 *
 * 业务风险：
 * 联系人或消息归属错误会造成用户把私密内容发送给错误身份。
 *
 * 外部资源与收尾：
 * 本场景不消耗 testnet 资金；测试联系人由本场景创建并在结束时清理。
 *
 * 覆盖需求：KM-INIT-001、KM-CONTACT-001、KM-MESSAGE-001。
 */
```

### 6.2 `test.step` 规范

步骤名称描述业务进展，不描述控件操作：

```ts
await test.step("用户创建第一个本地保险箱和身份", async () => { /* ... */ });
await test.step("用户把对方保存为联系人", async () => { /* ... */ });
await test.step("刷新后仍能找到联系人和刚才的消息", async () => { /* ... */ });
```

禁止使用：

```text
点击 Next
填写 input
等待 locator
调用 coordinator method
```

Driver 内部可以使用这些技术操作，但其注释应说明“为什么必须这样等待/校验”以及失败对应的业务后果。

### 6.3 技术断言表达

技术断言保留精度，并在邻近注释说明业务含义。例如：

```ts
// URL 改变只说明页面开始跳转；只有当前 Key 和运行时能力同时就绪，
// 用户才真正完成初始化并可以继续使用后续业务。
await expect.poll(readRuntimeOutcome).toBe("ready");
```

允许 Gate 直接验证协议版本、消息端口、epoch、generation、CAS、撤权顺序和错误码。此类文件仍必须在文件头说明它保护的业务结果，不能只罗列技术名词。

### 6.4 禁止模式

1. Journey 直接散落 CSS 结构选择器或实现私有字段。
2. 注释逐行翻译代码，没有业务信息。
3. 用固定睡眠代替明确的业务就绪或失败条件。
4. 为了报告好看吞掉浏览器错误、远端错误或清理错误。
5. 一个巨大 Journey 覆盖所有功能，导致任意失败都无法定位。
6. 把多个互相依赖的 `test()` 伪装成可复用业务链。

## 7. Flow、Driver 与场景状态

### 7.1 Flow 契约

Flow 输入和输出使用显式状态类型，让调用者看出业务前置条件：

```ts
/** 尚未建立 Keymaster 身份的全新浏览器状态。 */
type FreshUserState = { page: Page };

/** 已完成初始化、已解锁并选中一把可用 Key 的业务状态。 */
type ReadyUserState = {
  page: Page;
  bucketLabel: string;
  keyLabel: string;
  publicKeyHex: string;
};

async function initializeNewLocalUser(
  state: FreshUserState,
): Promise<ReadyUserState>;
```

Flow 必须：

1. 明确业务前置状态和完成状态；
2. 自己验证本过程承诺的关键结果；
3. 不依赖另一个 Playwright test 留下的状态；
4. 不直接读取长期秘密；
5. 不擅自创建或销毁不在自身契约中的外部资源；
6. 失败时保留足够的脱敏上下文供 Journey 报告。

### 7.2 Driver 边界

Driver 负责：

- 可访问性 selector 和页面操作；
- 生产 parser/schema 的协议交互；
- 明确的就绪屏障和失败识别；
- 浏览器、Window、SharedWorker、Service Worker 和远端事件的技术证据；
- 将底层错误转成 Flow 能表达的业务失败，但不丢失原始脱敏错误码。

Driver 不负责决定一个完整 Journey 的业务顺序。

## 8. E2E 专用资源配置

### 8.1 固定资源目录

已经确定以下目录和文件专用于 E2E：

```text
/home/david/.config/keymaster-e2e/
├── s3.json
├── satsubscription.json
└── seed-key.hex
```

资源含义：

| 文件 | 中文用途 | 敏感等级 |
| --- | --- | --- |
| `s3.json` | 本次测试直接使用的 S3 物理桶连接配置和凭据 | 高 |
| `satsubscription.json` | 服务于 testnet 的 SatSubscription WebSocket/WebRTC Direct 地址 | 当前为公开连接信息；仍按配置文件保护 |
| `seed-key.hex` | 持有 testnet 测试币的资金种子私钥 | 最高 |

默认通过一个环境变量定位目录：

```text
KEYMASTER_E2E_CONFIG_DIR=/home/david/.config/keymaster-e2e
```

不把私钥或 S3 Secret 展开成命令行参数，也不使用 `VITE_` 前缀传入浏览器构建。

### 8.2 权限和路径门禁

资源准备阶段必须 fail closed 地检查：

1. 配置目录的真实路径位于 Git 工作树之外；
2. 目录归当前运行用户所有且权限不宽于 `0700`；
3. `s3.json`、`satsubscription.json`、`seed-key.hex` 归当前用户所有且权限不宽于 `0600`；
4. 文件不是指向仓库内或公共目录的符号链接；
5. JSON shape、URL、私钥格式和必要字段合法；
6. 错误消息只报告文件名、缺失字段和权限问题，不输出字段值。

当前配置在实施前需要人工收紧权限；测试框架不得自动修改用户文件权限后假装检查通过。

### 8.3 秘密传播边界

1. 只有 Node 侧 Resource 层可以读取 `seed-key.hex` 和 S3 凭据。
2. Journey、Flow、浏览器 `localStorage`、Playwright `storageState` 和测试附件不得包含长期秘密。
3. 错误对象、日志、trace、截图、视频、HTML 报告和 JSON 证据必须经过脱敏门禁。
4. 资金种子私钥不得导入 Keymaster 浏览器；浏览器只使用本次 Journey 的一次性测试 Key。
5. 敏感字符串不得作为普通对象字段被序列化；使用最小生命周期的封装，使用完成后尽力清零 Buffer。
6. CI 使用 Secret Store 在临时 `0700/0600` 目录物化相同文件结构；任务结束删除临时目录。

## 9. S3 桶生命周期

### 9.1 清理作用域

S3 物理桶直接使用 `s3.json` 给出的值，不要求桶名称带有 `keymaster-e2e`，也不要求额外的
purpose 或 ownership 文件。每次完整 `real-resource` E2E 运行开始前，非前缀 setup 执行一次
指定桶的全量业务对象清理；不是每个 test、每个 retry 或每个 worker 清理一次。

一轮运行定义为一次顶层测试命令产生的唯一 `run_id`。相同 `run_id` 的 setup 重试只复核或继续未完成清理，不把已经开始的 Journey 数据再次删除。

### 9.2 清理作用域

测试按是否声明对象前缀选择清理作用域：

1. 前缀测试传入 `run_id/scenario_id/`，只分页删除该前缀下的对象、版本、delete marker
   和 multipart upload；
2. 非前缀测试不传 prefix，分页删除指定桶中的全部业务对象；
3. 两种模式都必须先取得当前运行的 `.keymaster-e2e/lease.json`，避免两个 real-resource
   运行同时操作同一个桶；
4. `s3.json`、目录权限、文件类型和必要连接字段仍由本地 loader 检查，但不做“是否专用桶”
   的额外判断。

lease 或清理操作失败时保持失败，不把连接成功误报为测试成功。

### 9.3 清理内容

清理器必须：

1. 分页列出并删除所有普通测试对象；
2. 若启用版本控制，删除历史版本和 delete marker；
3. 中止遗留的 multipart upload；
4. 清理期间保留当前 `.keymaster-e2e/lease.json`，其它业务对象不因路径带有控制前缀而豁免；
5. 删除后重新分页确认没有业务对象残留；
6. 只在确认完成后写入脱敏运行账本。

### 9.4 并发与收尾

1. setup 项目获得远端 lease 后才允许其他 Journey 开始。
2. CI 对同一资源配置使用 concurrency group，禁止两个运行同时清理/消费同一桶。
3. Journey 使用 `run_id` 和 `scenario_id` 隔离其业务对象；不得共享模糊的固定名称。
4. 成功结束后再次尽力清理本轮对象并释放 lease。
5. 异常退出由下次启动时的强制清理收口。
6. 本地仅可通过显式调试开关暂时保留失败数据；CI 禁止保留。

## 10. testnet 资金生命周期

### 10.1 资金角色

`seed-key.hex` 是 E2E testnet 资金库的种子私钥。私钥本身没有网络属性，因此实现必须在资金管理器内部硬编码并验证 testnet 地址、查询和广播路径，调用者不能传入或切换为 mainnet。

资金模型：

```text
长期 testnet 资金库（seed-key.hex，只存在于 Node Resource）
        ↓ 提供限定金额
一次性 Journey 测试钱包
        ↓ 导入/生成业务状态并执行测试
结束后由 Resource 归集剩余 testnet 资金
```

### 10.2 启动检查

资金管理器必须：

1. 校验私钥是合法的 secp256k1 标量；
2. 只派生和报告 testnet 公钥地址，不报告私钥；
3. 查询 confirmed、unconfirmed、可安全花费 UTXO 和当前链状态；
4. 验证余额达到本轮预算和安全余量；
5. 检查同一资金库没有另一个活动运行；
6. 对应 mainnet 地址一旦发现真实余额，fail closed 并提示人工处置；
7. 不把余额查询结果对象与私钥放在同一个可序列化结构中。

### 10.3 一次性钱包和资金预算

1. 每个需要真实资金的 Journey 使用独立一次性钱包，不并行复用一个花费状态。
2. 每个 Journey 声明最大充值额、预计手续费和最大允许损失。
3. 超出预算必须在执行前停止，不能运行到转账中途才发现资金不足。
4. 一次性私钥只保存在仓库外的受限 runtime 目录，权限 `0600`。
5. runtime 恢复文件必须与 `run_id/scenario_id` 绑定，完成归集后删除。
6. 长期资金种子绝不进入浏览器；如业务必须导入私钥，只导入本次一次性钱包。

### 10.4 结果未知和恢复账本

每次充值、业务转账和归集记录不含秘密的恢复账本：

| 字段 | 中文含义 |
| --- | --- |
| `run_id` | 本轮 E2E 运行编号 |
| `scenario_id` | 使用资金的业务场景编号 |
| `wallet_address` | 一次性测试钱包公开地址 |
| `funding_txid` | 资金库充值交易编号 |
| `funded_satoshis` | 本次提供的聪数 |
| `business_txids` | 本场景产生的业务交易编号 |
| `return_txid` | 剩余资金归集交易编号 |
| `status` | `prepared/funded/returning/returned/uncertain` 的中文定义状态 |

广播超时或连接中断时，禁止把“没有收到响应”解释成“没有广播”并直接重发。必须先根据 txid、输入 UTXO 和余额对账，再决定继续等待、归集或报告人工处理。

### 10.5 测试产物保护

1. 导入一次性私钥的真实资金 Journey 不保留可能捕获输入值的 trace、视频、截图或 DOM snapshot。
2. 此类场景以脱敏步骤、地址、txid、金额、余额变化和链上状态作为审查证据。
3. “导入私钥 UI 是否正确”另用不含资金的确定性一次性 Key 完成可视化测试，不能拿长期资金种子做 UI fixture。
4. 失败附件必须通过秘密扫描；检测到 64 位私钥、WIF、S3 Secret 或配置原文时，整项测试失败且禁止上传报告。

## 11. SatSubscription testnet 服务

### 11.1 配置契约

`satsubscription.json` 当前提供：

| 字段 | 中文含义 |
| --- | --- |
| `websocket` | 浏览器/客户端连接 SatSubscription testnet 服务的 WebSocket 地址 |
| `webrtc-direct` | P2P 客户端连接同一测试服务的 WebRTC Direct 地址 |

资源层读取并验证配置，Journey 不直接打开文件。

### 11.2 启动检查

每轮真实资源测试开始时必须证明：

1. WebSocket 可连接并完成正式握手；
2. WebRTC Direct 地址可解析，要求它的场景还必须完成真实连接；
3. 服务返回的货币网络是 `testnet`；
4. 服务支付地址属于 testnet；
5. 服务身份与预期一致，两个入口不能静默指向不同服务；
6. 失败信息区分“配置错误、服务不可达、身份不符、网络不符”。

不能因为文件名或人工说明中写了 testnet，就跳过运行时网络身份验证。

### 11.3 状态隔离

1. 每轮运行生成唯一 `run_id`；每个请求使用唯一 `request_id`。
2. 付费、重复请求、账本和余额断言按付款方、发布方、请求编号的正式业务身份域验证。
3. 服务端正式账本不是临时测试垃圾，不通过数据库删除伪造“恢复原状”。
4. 测试收尾归集客户端剩余 testnet 资金；服务收入和双向账本作为真实业务结果核对。

## 12. Playwright 资源编排

真实资源测试采用显式项目依赖：

```text
resource-setup
├── 权限与秘密预检
├── S3 排他 lease 和开场清理
├── SatSubscription testnet 健康检查
└── testnet 资金库预算/旧账恢复
        ↓
real-resource journeys
        ↓
resource-teardown
├── 一次性钱包归集
├── S3 本轮对象清理
├── 远端状态复核
└── 释放 lease
```

要求：

1. setup 是整轮一次，不是 worker fixture。
2. 资源准备失败时依赖它的 Journey 全部不运行，并报告明确阻断原因。
3. teardown 即使 Journey 失败也必须运行；进程级崩溃由下一轮 setup 的恢复步骤处理。
4. setup/teardown 在报告中独立显示，但不得输出秘密。
5. 不依赖固定 sleep 判断 S3、链上确认、P2P 或 Worker 是否就绪；必须轮询正式状态并同时识别终止失败。

## 13. 业务域覆盖基线

E2E-001 盘点时至少建立以下一级业务域。最终条目以当前代码和正式文档为准，不能把本表当成完整列表：

1. 首次初始化与 Local/S3 存储；
2. Vault、Key 创建、导入、选择、锁定、解锁、删除和恢复；
3. 首页、菜单、设置、语言、插件启停和导航；
4. 联系人、在线状态、消息、Channel 和通信恢复；
5. P2PKH 余额、同步、交易、广播、重组和 testnet；
6. BSV21、STAS、1Sat Ordinals 等资产能力；
7. SatSubscription、充值、消费、重复请求和账本；
8. Apps、Connect、App Identity、Session 和公开协议；
9. MSFile、文件读取、Range、媒体、WebRTC/WSS 和取消；
10. 其他正式装配业务插件及其公开入口；
11. Worker、插件生命周期、权限撤销、升级、恢复和不可逆 I/O；
12. 目标部署、外部 App 和公共网络验收。

每个业务域至少建立：

- 一条最短成功 Journey；
- 一条跨页面或跨能力的典型完整 Journey；
- 关键输入/权限失败；
- 关键外部依赖失败；
- 刷新、重启或重新进入后的持久性/恢复验证；
- 与该域安全等级相称的并发、隔离和撤权验证。

### E2E-009：技术 Gate 与故障矩阵

#### 工作

补齐不适合作为页面 Journey 的技术 Gate：

- SharedWorker/Service Worker 真正物理运行与重启；
- MessagePort、协议 parser/schema 和 transferable；
- epoch/generation/identity 失效；
- revoke/fence/block admission 先于 drain/I/O；
- CAS 冲突、并发页面、离线和恢复；
- 结果未知的不可逆 I/O 不重放；
- secret 不进入日志、诊断、Window surface 和构建产物。

#### 验收

- 每个 Gate 文件头说明它保护的用户业务结果。
- 不用宽松 mock 代替生产 parser 或真实浏览器链路。
- 固定 sleep 不作为跨上下文就绪证明。
- 失败同时给出技术证据和业务影响说明。

### E2E-010：现有 E2E 归档和迁移

#### 工作

1. 逐一审查现有 E2E spec，并把它们归一到 `e2e/integration/`。
2. 可表达用户目标的测试迁入 Journey/Flow/Driver。
3. 纯底层安全和生命周期测试迁入 Gate。
4. 临时 spike 明确保留理由、替代计划或删除条件。
5. 相同需求只保留一个覆盖真值，避免两个测试互相矛盾。

#### 验收

- 现有测试没有因重构静默丢失断言。
- 每个保留测试都有需求编号、层级和业务意义说明。
- 重复测试明确区分不同证据层级或完成合并。

### E2E-011：CI、报告和发布门禁

#### 工作

1. PR 默认运行 `local-integration`。
2. `real-resource` 使用受保护 Secret、非并发资源组和显式触发/定时计划。
3. `deployment-acceptance` 绑定不可变 Build ID。
4. 生成业务域、需求、场景、资源、清理和证据汇总。
5. 报告未执行、阻断、失败、清理失败和结果未知，不只统计 pass/fail。

#### 验收

- 没有真实资源的贡献者仍可运行本地完整层级。
- Secret 不出现在 CI 命令、日志和 artifacts。
- 一个层级通过不会自动提升另一个层级状态。
- 清理失败或资金 `uncertain` 会阻断真实资源验收通过。

### E2E-012：最终覆盖审查

#### 工作

1. 从生产代码反向审计覆盖矩阵。
2. 从覆盖矩阵正向定位到 Journey/Gate 和最近证据。
3. 抽查报告能否由不了解代码的检查者复述用户目标和结论。
4. 对秘密、资金、S3 删除和不可逆 I/O 做独立安全审查。

#### 验收

- 不存在孤立业务能力、孤立需求编号或孤立测试。
- 所有“已覆盖”条目都有对应层级的有效证据。
- 所有 Journey 业务注释合格，所有关键技术 Gate 没有被业务化表达掩盖。
- S3、testnet 资金和 SatSubscription 资源账本闭合。

以下情况必须停止真实资源测试，不能降级后继续并宣称通过：

1. 配置或秘密文件权限不合格；
2. S3 lease 或清理结果不确定；
3. seed-key 余额、UTXO 或网络归属不能确认；
4. SatSubscription 服务身份或 testnet 网络不能确认；
5. 存在上一轮未对账的资金 `uncertain`；
6. 脱敏器或秘密扫描失败；
7. 目标部署 Build ID 不可验证。

## 17. 非目标

1. 本施工单不在当前阶段实现测试代码。
2. 不为了提高覆盖数字重复创建没有业务或风险价值的场景。
3. 不把所有业务塞进一个无法定位失败的超长测试。
4. 不通过测试专用生产后门跳过正式 Keymaster 业务链路。
5. 不使用 mainnet 资金或把 testnet seed 暴露给浏览器。
6. 不因为使用前缀测试就省略 S3 清理确认、资金对账或秘密保护。
7. 不把自动化测试通过直接等同于尚未实际执行的公共部署验收。
