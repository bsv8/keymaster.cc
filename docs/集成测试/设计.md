# 集成测试设计

## 1. 运行模型

```text
Journey（用户完成一个目标，Playwright 报告单位）
    ↓
Flow（显式输入/输出的业务过程）
    ↓
Driver（页面、协议、Worker 和就绪屏障）
    ↓
Resource（S3、testnet、SatSubscription 等 Node 资源）

Gate（独立技术证据：存储、Worker、协议、生命周期和秘密边界）
```

Journey 不能读取长期秘密，也不能依赖上一个 `test()` 留下的浏览器状态。Flow 不注册
Playwright 测试；需要共享不可重复资源时由 Resource 的显式生命周期负责。Gate 不伪装成
用户旅程，必须有稳定的 `G-` 编号和中文业务影响说明；用户旅程使用 `J-` 编号。所有
Playwright spec 都位于 `e2e/integration/`，并按 `journeys/<层级>/` 或
`gates/<边界>/` 归档，执行档不会因为扫描目录而交叉收集同一个 spec。

## 2. 场景状态

`FreshUserState` 表示没有 Keymaster 历史数据的浏览器；`ReadyUserState` 表示存储已就绪、
Vault 已解锁且有 active Key。状态类型写在 `e2e/integration/support/types.ts`，Flow 的输入和
输出必须把业务前置条件写出来。密码等短期秘密只在调用栈中使用，不能进入附件、日志、
`storageState` 或矩阵证据。

## 3. 就绪屏障

页面 URL 改变不等于业务完成。Driver 必须同时检查页面结果、运行态/Key 结果和必要的
浏览器技术事实；跨页面、Worker、S3、P2P 和链上确认统一使用正式状态轮询，并识别终止失败。
固定 `sleep` 不能作为完成条件。

## 4. 资源生命周期

真实资源由独立的 `resource-setup` 和 `resource-teardown` 项目管理。Setup 对配置路径、权限、
所有权、网络身份和旧账进行 fail-closed 预检，成功取得 S3 lease 后才允许 Journey 开始。
Teardown 即使 Journey 失败也运行；下一轮 Setup 负责收口进程崩溃遗留。

## 5. 业务注释

每条 Journey 文件头必须说明：谁在用、开始状态、用户目标、成功标准、业务风险、外部影响
和收尾方式。步骤描述用户业务进展，例如“用户创建第一个本地保险箱和身份”，而不是“点击
Next”。技术断言旁边保留为什么它决定业务成立的中文说明。

## 6. 证据与失败

浏览器错误、底层错误码和外部资源结果都进入脱敏证据。脱敏器发现 64 位私钥、WIF、S3
Secret 或已知配置值时，场景失败且禁止附件上传。`uncertain` 结果不自动重试不可逆操作，
必须先用 txid、输入和余额对账。
