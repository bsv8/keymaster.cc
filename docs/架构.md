# Keymaster 架构

## 分层

这里按**职责**区分基础系统与插件，再分别说明 API 和 UI；不能从包名、是否使用插件
装配、是否允许禁用或 manifest 的 `kind`（产品分类）直接推导职责。

| 职责 | 含义 | 示例 |
| --- | --- | --- |
| base API（基础能力） | 全系统共用、由宿主维护统一真值或授权的能力 | 中央存储、Vault、会话与生命周期、能力和界面注册表 |
| base UI（基础能力界面） | 依附基础能力的观察、管理与跨插件聚合界面 | 应用外壳、系统设置、插件管理、全钱包存储只读浏览 |
| 服务插件 | 向其它模块提供某一类服务，可有自己的配置和状态界面 | WOC、MSFile、SatSubscription、P2P 服务 |
| 业务插件 | 拥有具体领域的行为、数据和界面 | 联系人、P2PKH、代币、扑克、应用启动器 |
| 公共 UI 组件库 | 各类界面复用的展示组件 | `packages/ui` 中的 Button、Modal、DataTable |

存储只读浏览器观察的是全钱包的逻辑存储空间，跨越单个插件的模块边界，因此职责上
属于 base UI。它的页面仍可由内置 Storage 产品的 Window 单元装配，服务实现仍归
中央存储所有；这两件事并不冲突。base UI 不因此得到任意访问权限，跨模块浏览必须
使用单独授权的只读能力，普通模块的存储用途声明仍然有效。

基础能力也可以采用插件产品的装配机制。`base` 当前不是一个 `PluginKind` 枚举值，
上述职责划分不表示代码已完成分类迁移。存储浏览器当前已有实现，真实浏览器验收已覆盖
JSON 预览、渲染量上界、锁定清空与窄屏键盘；Markdown/TXT 渲染与超大目录翻页仍未验证，
逐条状态见[存储浏览器施工单](./proposals/storage/存储浏览器施工单.md)。

### 当前物理位置

| 位置 | 当前承担的职责 |
| --- | --- |
| `packages/contracts` | 跨包契约全集，既有基础能力契约，也有联系人、P2PKH、WOC 等领域契约；不等于基础 API 的全部实现 |
| `packages/runtime` | WebLoom 的 Keymaster 适配、领域注册表、React 消费接口 |
| `packages/platform-storage` | 中央存储实现、页面侧代理，以及全钱包浏览界面；产品 id 为 `storage` |
| `packages/plugin-vault` | 基础密钥与会话能力，以及它自己的管理界面 |
| 其它 `packages/plugin-*` | 基础界面、共享服务或具体业务；目录前缀只说明包装方式 |
| `apps/web/src/shell` | 外壳、导航、路由渲染、初始化和锁定界面 |
| `apps/web/src/system` | 资产、藏品、转账和 BSV 链设置等聚合工作区 |
| `apps/web/src/coordinator`、Coordinator Worker 入口 | 运行单元装配、系统授权和领域服务的运行协调 |
| `packages/ui` | 公共 React 展示组件与格式化工具；不承担基础系统页面的统一归属 |

`apps/web` 目前还拥有聚合工作区和 Coordinator 领域协调逻辑，并非只做入口装配。
也不是所有页面都属于某个带 manifest 的产品：`registerAssetWorkspace` 在解锁后的
装配阶段注册资产、藏品、转账和链设置页面，并在 Owner 生命周期结束时释放它们。

## 当前产品分类与实际边界

### 同名字段不能混读

| 字段 | 取值 | 回答的问题 |
| --- | --- | --- |
| `PluginManifest.kind` | `core / platform / business` | 这个产品被归到哪一类 |
| `Capability.kind`（能力类型） | `local / rpc / stream` | 能力采用什么发布和调用形态 |
| `PluginState.kind`（运行状态） | `enabled / disabled / blocked` 等 | 产品此刻处于什么状态 |

当前产品分类只有三类，没有 `local` 产品。`plugin-protocol`、`plugin-bsv-price` 和
`plugin-key-import` 的 manifest 文件中都出现了 `kind: "local"`，但这些字段位于
`defineCapability` 调用中。它们的产品分类分别是 `platform`、`business`、`business`。
`local` 也不表示该能力只访问本地数据，例如 `woc.service` 同样是本地能力对象。

### 分类、启停、展示、寿命与授权分别声明

| 字段或目录 | 中文含义 | 实际作用 |
| --- | --- | --- |
| `kind` | 产品分类 | Keymaster 元数据；转换为 WebLoom manifest 时不传入，不决定通用生命周期和权限 |
| `displayGroup` | 插件管理页分组 | `core / platform / business / import / experimental`；管理页按它排序和显示，缺省回退到 `kind` |
| `startup` | 启动要求 | `required / optional`；`required` 还要求默认启用、不可禁用和提供能力 |
| `defaultEnabled` | 初始启用意图 | 未配置时采用的默认值；不是此刻已就绪的保证 |
| `canDisable` | 是否允许用户停用 | Window Host 的显式启停策略；当前插件管理页只列出值为 `true` 的产品 |
| `BUILTIN_ALWAYS_ON_PLUGIN_PRODUCT_IDS` | Worker 不可停用产品目录 | Coordinator 侧的产品策略，须与 manifest 保持一致；不按 `kind` 推导 |
| `bootstrapStage` | 进入启动流水线的阶段 | `storage-onboarding / vault-selection / owner-apps-ready / connect-apps-ready`；装配层明确禁止用分类猜阶段 |
| `units[].runtime` | 执行位置 | Window 或 Worker；不代表基础或业务职责 |
| `units[].scopeKind` | 实例寿命绑定 | `root / storage / owner-session / connect-session`；系统共用能力也可能随 Owner 会话重建 |
| 单元依赖、权限、存储声明与 Coordinator facade | 能力准入及授权 | 显式声明并由 Host/Coordinator 校验；`platform` 分类不会自动取得 `platform-only` 存储授权 |

因此，“基础职责”“不可禁用”“启动必需”“全局实例”“显示在设置下”是不同的判断。
当前清单中的 `core` 产品都不可禁用，但 Host 没有通过 `kind === "core"` 推导这个
策略。`platform` 产品中也同时存在不可禁用和可禁用产品。

### 当前发行版清单

当前 Web 清单包含 24 个内置产品、35 个显式运行单元。产品分类为 4 个 `core`、
7 个 `platform`、13 个 `business`。

| 当前 kind | 产品 id | startup | canDisable |
| --- | --- | --- | --- |
| `core` | `vault` | `required` | `false` |
| `core` | `home`、`settings`、`message` | `optional` | `false` |
| `platform` | `storage` | `required` | `false` |
| `platform` | `window-p2p`、`msfile`、`sat-subscription`、`protocol` | `optional` | `false` |
| `platform` | `woc`、`background` | `optional` | `true` |
| `business` | `contacts`、`webrtc`、`p2pkh`、`token-bsv21`、`token-stas`、`collectible-1satordinals`、`poker`、`importer-wif`、`importer-hex`、`importer-json-file`、`bsv-price`、`key-import`、`apps` | `optional` | `true` |

启动必需产品只有 `storage`、`vault`。不可禁用产品共有 9 个，与 Worker 的固定目录
一致；其余 15 个允许用户停用。只有 `poker` 默认关闭，其余产品默认开启。

展示分组也不能代替分类：`message.kind` 是 `core`，`displayGroup` 是 `platform`；
三个 `importer-*` 产品属于 `business`，但在 `import` 展示组。不可禁用产品被插件
管理页过滤掉，用户看到的列表不是完整产品目录。

## 职责对照与待清理事项

以下是对当前实现的职责判断和清理方向，**分类重划与结构调整均未实施**。

| 对象 | 当前归属 | 职责判断与待整理边界 |
| --- | --- | --- |
| 中央存储及全钱包浏览 | `storage`，`kind: platform` | 分别属于 base API 和 base UI；页面随 Storage 装配，不要求搬进公共组件库 |
| Vault 与密钥管理 | `vault`，`kind: core` | 基础授权能力及其管理界面；应与 Storage 在职责划分上保持一致 |
| 首页、设置、插件管理、系统状态 | `home / settings`，`kind: core` | 基础界面；具体服务的配置面仍由服务拥有 |
| 消息业务 | `message`，`kind: core`、展示组 `platform` | 消息列表、发送和历史是领域行为；应与底层 Channel/会话能力区分，固定开启策略另行声明 |
| Connect 协议与确认界面 | `protocol`，`kind: platform` | 统一外部授权入口具有基础职责；应与可选应用启动器分清关系 |
| 导入工作区与格式解析器 | `key-import`、`importer-*`，均为 `business` | 工作区聚合 Vault 和导入注册表；应区分基础密钥管理 UI 与可扩展格式解析实现 |
| 资产、藏品、转账聚合工作区 | `apps/web/src/system`，没有产品 kind | 需要明确跨插件聚合界面的宿主归属，具体资产行为仍由提供者拥有 |
| WOC 与链设置页面 | 服务为 `woc`，设置页面在 `apps/web/src/system` | 当前消费者依赖 WOC 契约；尚未建立“链上数据插件 → 多提供者”的完整产品结构 |
| P2P、MSFile、SatSubscription、后台服务 | `kind: platform`，启停策略不一 | 需分别区分统一宿主机制、具体服务实现和配置界面，不能仅因被多插件使用就视为基础授权层 |
| 联系人、P2PKH、代币、扑克、WebRTC、行情、应用启动器 | `kind: business` | 具体领域或可选集成；共享自己的 API 不会自动变成基础系统 |

清理时先以职责说明为准，再决定是否让 `core` 对应基础系统、`platform` 对应共享
服务、`business` 对应具体领域。若采用这个对应关系，Storage 与消息的现有分类就
需要重划；这不能通过移动页面目录或调整导航分组代替。启停、执行位置、寿命和权限
继续使用各自的显式声明。

链上数据目前并非完全没有抽象：`chain-height.reader` 已提供独立的高度读取契约，
但通用交易、UTXO 及代币查询仍消费 `woc.service` 和 WOC 专用契约。支持 `other`
提供者需要先明确公共数据契约、提供者选择和生命周期，不能只增加一个父分类。

包边界检查也有待补齐：`scripts/check-boundaries.mjs` 的通用插件互导扫描按
`plugin-*` 目录前缀识别产品，未把 `platform-storage` 纳入这组检查，也不按 `kind`
约束依赖方向。Worker 检查覆盖另一组执行环境规则；现有检查通过不代表基础职责与
服务、业务的分层已经得到完整校验。

## 三个执行位置

| 位置 | 中文职责 |
| --- | --- |
| Window（页面） | 渲染界面、接收用户输入，以及执行必须依赖浏览器页面的网络能力 |
| Coordinator SharedWorker（共享协调器） | 多页面唯一的钱包 Key、Owner 会话、任务、存储授权和服务运行态 |
| Service/Dedicated Worker（专用工作线程） | 媒体 Range 桥、隔离计算或单次会话能力；不成为第二个系统真值 |

跨位置只传可校验的数据和受限服务代理，不传插件上下文、Provider、密码或私钥。

## 运行作用域

```text
root
└─ wallet-storage（当前钱包的本地存储）
   └─ wallet-session（当前钱包会话）
      ├─ plugin-instance（插件实例）
      ├─ connect-session（外部 App 会话）
      └─ request（单次请求）
```

子作用域不能活过父作用域。锁定、钱包重置或重新导入时先撤销授权，再等待可等待的清理；
外部结果未知的操作不自动重放。

## 稳定边界

- 私钥操作只能通过 Vault 的操作式能力执行，业务代码不能读取私钥字节。
- 插件只能使用 manifest 明确声明的能力和存储用途。
- 插件菜单、路由和首页入口由对应插件声明，Shell 消费注册表；系统聚合工作区目前
  由 `apps/web/src/system/registerAssetWorkspace.ts` 注册，不在 Shell 再维护一份清单。
- WOC 请求统一经过 WOC 服务。
- Window P2P Host 只有一个执行租约，MSFile 和 SatSubscription 复用不同 lane（网络通道）。
- Storage、Owner、插件和请求都带世代；迟到响应不能写入新会话。
- 第三方 App 只能通过 Connect 网关使用批准的能力，不能进入内部插件容器。
