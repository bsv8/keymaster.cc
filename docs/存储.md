# 存储边界

本文定义 Keymaster 的目标存储边界。它是架构约束，不是对当前实现的描述；当前代码与目标
不一致的地方列在“现状审计”中。

## 术语与目标模型

Keymaster 的业务与运行数据只有三层承载位置：

```text
浏览器 A / Tab 1 ─┐
浏览器 A / Tab 2 ─┴─ 浏览器 A Worker ─┐
                                       ├─ 远程存储
浏览器 B / Tab 1 ─┬─ 浏览器 B Worker ─┘
浏览器 B / Tab 2 ─┘
```

| 层 | 作用域 | 典型寿命 | 共享范围 |
| --- | --- | --- | --- |
| Tab 内存 | 一个页面实例 | 页面刷新或关闭前 | 当前 Tab |
| Worker 内存 | 一个浏览器中的 Keymaster Worker 实例 | Worker 重启前 | 同一浏览器中连接该 Worker 的 Tab |
| 远程存储 | 一个远程存储空间 | 由业务保留策略决定 | 获得同一身份和存储授权的所有浏览器 |

这里的“内存”只指 JavaScript 运行内存。`localStorage`、IndexedDB、Cache API、OPFS 等浏览器
持久化设施都不是 Tab 内存或 Worker 内存。Keymaster 仅允许 `localStorage` 作为远程存储的
设备引导程序；它是启动控制面，不是第四个业务数据层，具体限制见“设备引导存储”。Local
Provider 的桶对象使用 IndexedDB，并必须请求 persistent-storage 授权；其它浏览器持久化设施
默认禁止使用。

产品和业务代码统一使用“远程存储”这个概念。Local、S3、R2、S3-compatible 等只允许作为
远程存储接口之下的 Provider/测试适配器名称，不得影响上层的数据归属、正确性或性能设计。
上层必须始终把远程存储当作网络慢存储：异步、有延迟、可能断网、可能超时、可能发生并发
冲突，也可能得到结果未知的写入。

“桶”不再是上层存储类型。若 Provider 本身使用物理 bucket，或者平台需要一个远程空间 ID，
它们只是远程存储的连接与隔离细节；页面、插件和业务服务不应在 Local 桶与 S3 桶之间分支。

## 如何决定数据放在哪一层

数据位置不按“业务数据”“设置”“缓存”等名称机械分类。每一份数据都必须从业务和逻辑边界
回答以下问题：

1. 谁拥有它：一个页面、一个浏览器运行实例，还是使用同一远程空间的所有客户端？
2. 它应活多久：页面刷新后是否仍有效，Worker 重启后是否仍有效，换浏览器后是否仍有效？
3. 丢失后业务上发生什么：允许直接丢弃、可以从权威来源重建，还是会丢失用户行为、资产、
   授权、恢复能力或审计证据？
4. 多个浏览器同时修改时，产品期望覆盖、合并、拒绝冲突，还是只能由一个写者操作？
5. 它的读取新鲜度、保留期限、删除条件和安全级别是什么？

据此采用下面的放置顺序：

```text
只属于当前页面交互？
  └─ 是：Tab 内存
  └─ 否：是否只需在当前浏览器运行期内由多个 Tab 共享？
          └─ 是：Worker 内存
          └─ 否：业务是否要求跨 Worker 重启、跨浏览器或长期保留？
                  └─ 是：远程存储，并定义并发、恢复和保留语义
                  └─ 否：回到拥有它的最近一层内存
```

“写到远程以后方便取”不是持久化理由；“它看起来像运行状态”也不是禁止持久化的理由。
例如，结果未知事务的恢复记录、幂等键、可恢复上传记录、用户可见历史和安全审计，虽然由
系统流程产生，只要业务承诺跨重启恢复或追溯，就可以属于远程存储。反过来，当前选择、
在线状态或同步游标即使容易序列化，如果没有跨浏览器业务语义，也不应为了同步方便而落盘。

可重建数据也不是一律禁止持久化。若重建成本本身是产品问题，可以把它设计成远程持久副本；
但必须写明它的权威来源、允许陈旧多久、失效与重建条件，不能让副本悄悄成为第二真值。

## 三层职责

### Tab 内存

Tab 负责页面交互和展示。适合放置：

- 未提交的表单、导入草稿、密码和凭据输入；
- 组件状态、路由状态、弹窗状态、乐观 UI 和当前页面错误；
- 当前 Tab 的请求句柄、取消句柄、订阅句柄和展示缓存；
- Worker 事件在当前页面中的只读投影。

Tab 刷新后这些数据默认丢失。确有恢复要求的数据，必须先定义恢复的业务语义，再通过 Worker
提交到远程存储，不能由页面自行写浏览器持久化设施。

Tab 不直接持有远程 Provider，不直接拼远程路径，不直接决定 CAS 版本，也不把页面缓存当作
授权依据。多个 Tab 的一致性来自 Worker 发布的运行态事件，不来自 Tab 之间互写持久化数据。

### Worker 内存

Worker 是一个浏览器内的运行权威和远程存储访问入口。适合放置：

- 当前解锁身份、解密后的私钥字节、明文连接凭据和 Provider 实例；
- 当前激活的 Key、会话 epoch、generation、能力 grant 和端口绑定；
- 浏览器内锁、I/O lease、请求队列、single-flight、AbortController 和在途 Promise；
- 定时器、在线状态、连接状态、任务实例、并发计数和背压状态；
- 有界读缓存、事件快照、去重窗口和可丢弃的派生视图。

Worker 重启必须能够从“远程持久真值 + 用户重新认证或宿主重新注入的秘密”重建。不能把旧
Worker 的锁、lease、grant、活跃连接或运行世代从远程存储恢复成仍然有效。

Worker 内存只在当前浏览器中共享，不是跨浏览器真值。浏览器 A 与浏览器 B 各自有 Worker；
二者的一致性必须通过远程版本、CAS、重读、轮询或远程变更通知完成。

### 远程存储

远程存储承载业务明确要求长期存在或跨客户端共享的数据。常见但不穷举的例子包括：

- 用户创建或接收的内容、资产相关记录和不可替代的业务状态；
- 用户设置、系统设置、策略、插件启停意图和授权决策；
- 加密后的 Key/Hold、连接秘密或其它必须持久保存的安全材料；
- 有跨重启语义的登录授权、事务日志、幂等记录、恢复记录和结果未知记录；
- 产品承诺保留的历史、审计、扣费记录和上传恢复元数据；
- 经明确设计的持久索引或远程数据副本。

每个远程数据声明必须同时说明：

- 稳定 owner（系统、远程空间、身份、App 或业务实体）；
- 用途和 schema 版本；
- 权威来源，以及它是主真值、日志还是可重建副本；
- 写入冲突策略和幂等键；
- 读取新鲜度、失效/重建方式；
- 保留、归档和删除条件；
- 是否含秘密，使用何种加密和最小授权。

远程存储不得保存 JavaScript 对象句柄、`CryptoKey`、明文私钥/密码/长期凭据、端口、回调、
Promise、计时器、浏览器锁、Worker 身份或运行期 capability。高频心跳、鼠标/页面活动时间、
在线 presence、队列长度等也不得直接写远程；若业务确实需要历史统计，应另行定义低频、
脱敏、可保留的业务记录。

## 访问与一致性规则

所有生产远程 I/O 都走以下单向链路：

```text
Tab ──受限命令/查询──> Worker ──RemoteStorage API──> 远程存储
Tab <────事件/结果──── Worker <────版本化结果─────────┘
```

- 插件和页面只能拿到按 owner、module、purpose 预绑定的受限句柄，不能拿 Provider、凭据或
  物理前缀。
- Worker 可以缓存远程读取，但缓存必须绑定远程版本与当前 session/generation；缓存命中不能
  绕过授权检查。
- 用户写入只有远程提交成功后才能报告成功。超时导致结果未知时，进入查询/恢复流程，不能
  当作失败后盲目重放。
- 跨浏览器可修改的数据必须使用 CAS、事务或领域级冲突合并。Worker 内串行队列只能解决
  同一 Worker 的竞争，不能证明跨浏览器安全。
- 远程读取必须分页、限流并允许取消。UI 渲染、键盘输入和高频事件路径不得同步等待远程 I/O。
- 不默认在启动时加载整个远程空间。启动只加载恢复运行所需的最小清单，其余按页面和任务
  需要读取。
- 离线时只能展示有明确陈旧标记的 Worker 缓存；没有远程确认的修改不能伪装成已经保存。

## 当前代码映射与审计

以下结论来自当前契约、中央声明和 Coordinator 实现，用于指导后续拆分，不表示仅列出的数据
才允许存储。

### 已符合或基本符合目标的位置

| 当前数据 | 当前代码语义 | 目标判断 |
| --- | --- | --- |
| Hold 私钥密文、Vault 公开索引与生命周期日志 | 远程对象/K-V，明文私钥留在 Worker | 有长期恢复与安全语义，属于远程存储 |
| 联系人、铸造/会话历史 | Owner 级中央 K-V | 是否保留由各业务契约决定；现有用户内容/历史语义支持远程存储 |
| 私密消息证据（sent/received raw、timeindex） | Owner 级 files（`<owner>/messages/…`，内容寻址文件名 + 只增时间索引） | 只存 raw 证据与本机观察时间，不存解析投影；raw 缺失时显示缺失，不重建索引 |
| Coordinator 设置、插件启停意图 | 桶级 snapshot | 属于跨客户端系统设置时应在远程存储 |
| 当前选中 Key | 浏览器 session 的 `activeKey`（设备本地 JSON），Worker 读取一次后内存缓存，切换/锁定等固定动作写透 | 每浏览器一个运行上下文，已不写远程桶 |
| Protocol origin policy、fee pool | 桶级 K-V | 授权策略和资金业务状态具有持久语义，应在远程存储 |
| Protocol 终态命令记录 | 只把终态摘要写入 command history | 若产品承诺用户可追溯历史，属于远程存储；中间态仍应只在 Worker |
| Connect session record | 保存 owner、origin、claims、吊销状态，不保存 runtime binding | 若产品承诺跨刷新 `resume/logout`，这是持久授权真值；对应的活 runtime/grant 仍只在 Worker |
| multipart 恢复元数据 | 独立中央 purpose | 只有在产品承诺跨重启续传时属于远程；分片字节、活请求和 client 句柄不属于远程 |
| SharedWorker 的私钥、grant、请求队列、锁、lease、timer、presence | Worker 模块状态 | 属于 Worker 内存，方向正确 |
| 首次初始化页面草稿和秘密输入 | React state/请求对象 | 提交前属于 Tab 内存，方向正确 |

### 必须重新拆分或明确业务语义的位置

| 当前数据 | 发现的问题 | 目标处理 |
| --- | --- | --- |
| P2PKH `state` 大 purpose | 交易事实、本地广播恢复、input claim、链上派生 UTXO、同步游标和进行中 run 混在一个远程记录模型 | 按业务真值、结果未知恢复、可重建副本、纯 Worker 进度拆 purpose；逐项定义权威来源和保留期 |
| SatSubscription `subscription-state` | 期望配置、远端观察、SPI 结果/扣费审计和活连接状态容易被一个 snapshot 混合 | 配置、结果未知恢复和扣费审计可远程；连接句柄、online/degraded、当前订阅流放 Worker |
| MSFile `app-usage` | `firstSeenAt/lastSeenAt` 可能是审计，也可能只是运行统计 | 先确定产品是否承诺审计/策略依据；否则留 Worker 并做有界统计，不能因容易写入就持久化 |
| Protocol session 的 `lastUsedAt` | 每次业务调用刷新会把运行活跃度变成高频远程写 | 若只用于过期判断，改用低频 checkpoint 或固定 expiry；若是审计，拆成独立、限频的审计记录 |
| 各 Repository 的全量加载 | Protocol list、P2PKH record store 等会把远程 purpose 加载成 Worker 内存数据库 | 明确这是缓存而非第二真值，增加分页/按键读取、版本失效和容量上限 |

### 当前浏览器持久化需要收口到引导边界

当前代码还直接使用 `localStorage` 保存或承载：

- `keymaster.storage.catalog.v2`：远程空间目录、当前选择和加密连接配置；
- `keymaster.storage.initial-setup.recovery.v1`：初始化恢复账本；
- `keymaster.coordinator.worker-profile-id.v1`：SharedWorker 命名身份；
- `keymaster.themeMode`、`keymaster.languageMode`：系统显示设置。

Local Provider 的桶对象已经不在 `localStorage`：它使用受限 IndexedDB Provider
（`keymaster.local/objects`），页面必须显示 persistent-storage 授权条并在用户授权后
才视为可长期保留；未授权时浏览器仍可能在存储压力下清理。

这些数据不会因为改名为“RemoteStorage”就自动符合边界。只有远程定位、加密认证与恢复引导
所必需的最小数据可以留在 `localStorage`；其余内容必须回到三层模型。Local Provider 仍是
开发/测试适配器，复用统一接口，并且上层仍按网络慢存储设计；它不能证明跨浏览器一致性，
也不能作为生产远程存储能力的验收依据。

主题和语言不是远程连接的引导信息，不能使用这个例外。若它们是跨客户端系统设置，应以远程
值为真值；首帧先使用浏览器/系统默认，远程设置加载后再应用。若将来产品明确把它们定义成
设备偏好，需要另行扩展引导层契约，不能由实现自行把任意设置写入 `localStorage`。

## 设备引导存储

刷新或重新打开浏览器后，Worker 内存已经消失，而连接远程存储至少需要远程位置、认证方式
或可派生身份。这些信息不能只保存在它所指向的远程存储里，否则形成启动循环。因此
`localStorage` 被明确限定为设备引导存储。

设备引导存储只允许保存：

- 远程存储的稳定 ID、显示标签、Provider 类型和连接位置；
- 经过认证加密的连接凭据，以及解密所需的公开 KDF 参数；
- 当前选用哪个远程存储的设备级指针；
- 本机以何种方式接入远程存储：创建新空间或连接已有空间；
- 远程初始化事务 ID、远程空间 ID 和状态指纹等最小恢复指针；
- 为同一浏览器选择正确 Worker 实例所必需的安装/配置身份。

它明确禁止保存：

- 任何业务内容、Key 列表、远程系统设置、授权策略和用户历史；
- 远程数据的缓存、副本、索引、搜索结果或离线镜像；
- 当前激活 Key、解锁状态、session、grant、generation、锁、lease、队列和 presence；
- 明文密码、明文私钥、明文长期凭据、`CryptoKey` 或可直接使用的运行 capability；
- 仅为了减少远程读取或方便 Tab/Worker 同步而复制的数据。

引导记录不是远程业务真值。它必须具有独立 schema、大小上限和严格字段白名单；字段未知、
解密失败或与远程身份不匹配时必须停止启动并要求重新连接，不能据此覆盖远程数据。

设备引导记录分成两种状态：

- **已提交连接**：已经通过远程身份和认证校验，可以用于冷启动；
- **恢复指针**：一次创建或接入操作尚未得到确定结果，只能用于查询和恢复，不能作为可用连接。

页面表单草稿仍只在 Tab 内存。用户输入的明文凭据、密码和候选配置不能为了防止刷新丢失而
写入设备引导存储。只有远程操作成功并核对远程身份后，才能提交加密后的本机连接记录。

### 创建一个新的干净远程存储

“干净”是指选定物理位置下的 **Keymaster 远程命名空间不存在**，不要求整个物理 S3 bucket
没有其它系统的对象。创建流程必须：

1. 规范化 Provider 和物理位置，确定唯一 Keymaster namespace root；
2. 探测读取、写入、删除和原生条件写能力；认证失败、无权限、超时、CORS、网络错误都属于
   “状态未知/不可访问”，绝不能解释成“命名空间不存在”；
3. 读取固定 root manifest。只有得到权威的 not-found，才允许进入创建；
4. 生成新的 `remoteStorageId` 和初始化事务 ID，以 `if-none-match`/CAS 条件创建远程事务记录
   和候选对象；任何已存在对象或竞争创建都必须停止并转入重新发现；
5. 写入初始 Hold、必要系统配置和业务根，最后以 CAS 发布 root manifest，令该远程空间正式
   可发现；manifest 发布前的对象都只是候选数据；
6. 重新读取并认证 root manifest、Hold 和事务结果；确认远程提交成功后，才把已提交连接写入
   设备引导存储并设为当前远程存储；
7. 若响应丢失或结果未知，只保存脱敏恢复指针。恢复时按事务 ID 和远程 manifest 查询，不得
   生成新的远程 ID 后盲目重做，也不得清理不属于该事务的对象。

创建流程不允许“先在 `localStorage` 宣布成功，再尝试补远程数据”。本机连接是远程提交结果
的索引，不是远程空间存在的证明。

### 连接一个已经存在数据的远程存储

连接已有空间是发现与认证流程，不是初始化流程。它必须：

1. 使用用户提供的 Provider、位置和凭据读取固定 root manifest；
2. 校验格式、schema、`remoteStorageId`、namespace root、完整性和所需能力，区分“不存在”、
   “无权访问”、“数据损坏”、“版本过新”和“暂时不可用”；
3. 使用远程 Hold/认证记录验证用户提供的密码或身份，并读取最小系统清单；
4. 只从远程数据恢复 Key 索引、系统设置和业务入口，不采信本机同名记录、旧 revision 或旧
   selected Key 覆盖远程内容；
5. 成功认证后，以 `remoteStorageId + 规范化物理位置` 去重并提交设备引导记录。已存在同一
   远程 ID 的记录应更新连接信息，而不是创建第二个逻辑远程空间；
6. 在连接阶段不创建 Hold、不写默认设置、不重置版本、不自动迁移、不删除未知对象。确需
   schema 迁移时，先完成独立的迁移计划、备份与 CAS 提交，再更新本机引导记录；
7. 远程空间暂时不可用时保留原已提交引导记录并报告不可用，不能降级成“新建空空间”。

如果固定位置不存在 root manifest，页面只能明确提供“创建新的远程存储”；如果 manifest
存在，页面只能进入“连接已有远程存储”。两条流程不能根据本机 catalog 是否存在自动互换。

### 冷启动与身份核对

无论最初来自“新建”还是“连接已有”，后续冷启动都使用同一流程：

```text
读取设备引导记录
→ 解密本机连接信息
→ 连接远程存储
→ 读取并认证 root manifest
→ 核对 remoteStorageId、物理位置指纹和 schema
→ 加载最小远程真值
→ 建立新的 Worker 运行态
```

引导记录中的远程 ID、revision 和状态指纹都只是预期值。每次冷启动必须以远程读取结果为准；
不一致时停止并进入重新连接或恢复流程，不能让本机旧记录把另一个远程空间挂到旧身份下。

初始化恢复账本必须拆成“本机恢复指针”和“远程事务真值”。`localStorage` 可以保存脱敏的
事务 ID、目标身份与状态指纹，以便 Worker 崩溃后找到恢复入口；事务阶段、幂等结果和对象
提交状态应由远端协议确认。远端结果未知时，本机记录只能触发查询或人工恢复，不能单独证明
事务成功或决定覆盖/删除远程数据。

当前 `keymaster.storage.catalog.v2` 同时含有允许的引导字段和不应持有的运行/远程状态字段，
需要按上述白名单重新定义。`keymaster.storage.initial-setup.recovery.v1` 需要缩成恢复指针；
Local Provider 的对象数据走受限 IndexedDB Provider，不属于引导信息，生产路径不得写入
`localStorage`。

## 代码约束与验收

后续实现至少应建立以下自动化门禁：

- 静态边界：Window/插件不得导入 Provider 或直接调用浏览器持久化 API；生产代码只有设备
  引导模块可以访问 `localStorage`，只有 Local IndexedDB Provider 可以使用 IndexedDB API，
  Cache API、OPFS 默认禁止。
- 持久化授权：IndexedDB 未获 persistent-storage 授权时，页面必须在 header 上方持续显示
  授权条；只有 `navigator.storage.persist()` 成功后才隐藏。
- 引导边界：`localStorage` key 与字段使用固定白名单，并验证不含业务数据、远程设置、缓存、
  运行态和明文秘密。
- 新建/接入边界：真实远程测试分别覆盖空 namespace 创建、已有 namespace 只读接入、竞争
  创建、权限错误不可误判为空、结果未知恢复、重复接入去重和已有数据零覆盖。
- 声明边界：每个远程 purpose 必须附带 owner、持久化理由、真值类型、冲突策略和保留策略；
  禁止使用含义宽泛的 `state`、`cache`、`misc` purpose 接纳不同寿命的数据。
- 生命周期：Tab 刷新只丢 Tab 状态；Worker 重启撤销全部运行授权并从远程重建；两个浏览器
  不共享 Worker 内存，但能通过远程版本观察同一业务真值。
- 慢存储：在注入延迟、断网、超时、CAS 冲突和结果未知后，UI 不阻塞、不假成功、不盲重放。
- 容量：远程读取分页，Worker 缓存有上限，历史和恢复记录有保留/清理策略。
- 安全：明文私钥、密码、长期凭据、CryptoKey 和活 capability 不出 Worker 内存；诊断与恢复
  记录保持脱敏。
