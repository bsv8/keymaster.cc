# 单 Key 本地存储需求

状态：已实现。本文替代此前的多桶、远程存储目标；多桶、多 Key 与 S3 体系已从契约、运行代码、界面与测试中移除。

## 已确认范围

- 同一浏览器配置、同一站点 Origin 中，只保存一把钱包 Key。
- 彻底取消桶、Key 列表、当前 Key 选择和切换。
- IndexedDB 是系统本地持久化的正式介质，保留文件、K-V、快照和跨重启恢复能力。
- 所有插件的持久数据读写只能通过同一个平台存储接口进行，按插件/模块归入工整的逻辑目录。
- 全部挖除原 S3 存储体系，不保留隐藏入口、远程 Provider 或兼容分支。
- 使用全新存储结构，不迁移、不合并、不自动导入旧桶数据。

这里的 Key 指钱包身份私钥；IndexedDB 记录键、K-V 业务键、App 发布者公钥、联系人及交易对手公钥仍可存在。单 Key 不限制业务对象数量，也不取消模块和 App 的权限隔离。

## 产品行为

### 初始化与冷启动

未初始化时只提供创建钱包 Key、导入钱包 Key 两种路径，不再选择存储类型、配置桶或连接已有远程空间。

创建或导入流程必须验证私钥材料或 KeyHold 文件，设置或验证 Key 密码，生成必要初始数据，再原子提交唯一 Key 和初始化标记。只有 IndexedDB 事务完成后才能报告成功。取消、写入失败或刷新不得留下被当作完整钱包使用的半成品。

导入来源沿用现有支持的私钥/KeyHold 输入能力，但最终只产生一把 Key。禁止追加第二把 Key。此功能不承担旧桶业务数据迁移。

冷启动只读取本地格式信息、唯一 KeyHold 和必要系统设置，不扫描 Key 目录、不恢复 selected Key、不建立远程连接。正常启动进入锁定状态；用户输入 Key 密码后，由 Worker 解锁唯一 Key。公开元数据损坏、格式不支持或初始化记录不完整时进入明确的错误/恢复界面，不能静默创建空钱包覆盖原数据。

### Key 管理

保留当前 Key 的公开信息、名称修改、锁定、解锁、修改密码和加密 KeyHold 导出。

KeyHold 保留现有文档加密格式及密码学实现，改为固定路径存放。取消文件名与公钥一致的要求，保留解密后私钥、公钥及本地身份记录一致性校验。只有 Key 密码一个持久秘密认证域；删除为 S3 连接凭据服务的启动密码及其 KDF 配置。

钱包已有 Key 时，创建/导入入口不能覆盖它。更换 Key 通过“重置钱包后重新创建或导入”完成，不提供原地替换身份并沿用旧业务数据的能力。

重置属于独立的破坏性操作：明确告知删除当前 Key 和新结构中的全部本地钱包数据，先撤销会话和任务权限，再原子清空钱包数据。失败时不得报告完成；旧授权不得因重置失败而自动恢复。重置成功后回到未初始化状态。

本地 reset 不撤销链上交易或服务端已经接受的操作；这类结果按对应业务恢复规则处理。

### 本地可用性

本地设置、联系人、消息证据、交易记录、恢复日志及 App 数据在刷新、Worker 重启和浏览器重开后可恢复。离线可使用本地数据；链上查询、消息传输、MSFile 和其它网络业务继续由各自契约决定可用性。

保留浏览器持久存储授权状态及配额错误处理。未获持久存储授权时可以使用，但必须明确提示数据可能被浏览器清理；不能把授权成功描述为备份或跨设备同步。

IndexedDB 打开、事务、配额或版本升级失败时给出可区分的错误，不回退到 localStorage 存业务数据，也不自动清空数据库。

## 存储分层与访问边界

| 位置 | 保存内容 | 生命周期与权威 |
| --- | --- | --- |
| Tab 内存 | 表单草稿、密码输入、页面视图、请求句柄 | 当前页面；不是持久真值 |
| Worker 内存 | 解密私钥、解锁状态、会话、grant、锁、任务、连接和有界缓存 | 当前运行实例；重启后重新建立 |
| IndexedDB | Key 密文、系统设置、业务记录、文件、授权决策和恢复证据 | 本浏览器本 Origin 的持久真值 |

访问链路固定为：页面/插件 → 受限命令与句柄 → Coordinator Worker → IndexedDB。

Worker 是授权、事务与业务提交的权威。若浏览器或宿主限制导致物理 IndexedDB 操作必须借助页面桥接，该桥接只能执行 Worker 预绑定的受限操作，不得决定身份、路径范围、版本或写入授权。

明文私钥只存在受控 Worker 内存，页面和业务插件继续通过受限密码学服务使用它。密码、明文私钥、运行 capability、Promise、端口和计时器不得写入持久存储。

localStorage 不再保存桶目录、连接凭据、activeBucketId、activeKey、S3 初始化恢复指针或启动密码参数。若宿主确需稳定 Worker 命名标识，只能保留独立的非秘密设备标识，并证明其必要性；不能用它承载钱包数据。

主题、语言和插件启停意图作为本地系统设置保存于 IndexedDB；首帧使用系统默认，读取完成后应用。

## 插件统一存储接口

平台只向插件暴露一个存储接口入口（暂称 `ctx.storage`），所有内置插件、第三方插件及其 Worker 侧业务代码都通过该入口读写本地持久数据。第三方 App 通过 Connect 获得该接口的受限代理，不能另建一套存储后端。接口的具体类型和方法名在实现设计时确定。

接口提供相对路径读取、写入、删除、分页列举、条件写入和原子批量提交；JSON 记录与二进制文件使用同一套路径、授权、错误和事务规则。JSON 便捷方法、K-V 或 snapshot 适配层只能建立在这个统一入口之上，不能各自打开数据库或绕过权限检查。

平台根据已验证的插件身份和中央声明预绑定目录、用途及读写权限。插件只传目录内的相对路径，例如联系人插件读取 `联系人01.json`，平台将其定位到 `contacts/联系人01.json`；插件不能自行指定根目录或借路径访问其它插件。允许跨模块共享时，必须由平台显式授权，继续走同一个接口。

插件不得直接使用 indexedDB、IDBDatabase、IDBTransaction、localStorage、OPFS 或自建持久存储 Provider；只有平台存储实现层可以操作底层数据库。插件内部 repository 可以封装领域逻辑，但所有持久 I/O 必须转发到统一接口。平台对 `key.json` 及系统保留区使用专门权限，普通插件不能因拥有文件接口而读写它们。

“同一个接口”指统一契约和入口；每个插件拿到的是权限受限的绑定实例，并非所有插件共享一个可以任意读写根目录的句柄。

## 单 Key 逻辑目录

目录是 IndexedDB 中的逻辑路径，不要求使用操作系统文件目录。

```text
/
├── key.json                            唯一钱包 Key 的加密 JSON 文档
├── .keymaster/
│   ├── meta                            本地格式、schema、初始化状态与身份世代
│   ├── system/<module>/<purpose>/      平台及系统持久数据
├── contacts/                          联系人插件目录
│   ├── 联系人01.json                   一联系人一文件（示意文件名）
│   └── 联系人02.json
├── messages/                          消息原始证据及时间索引
├── p2pkh/                             网络设置、交易与恢复文件
│   ├── setting.json
│   └── <network>/…                    按主网/测试网组织业务文件
├── p2p/                               P2P 设置
├── sat-subscription/                  本地供应商设置
├── msfiles/                           MSFile / BitFS 本地设置与业务文件
└── apps/                              第三方 App 存储根
    ├── <app-name-A>/                  App A 的独立授权目录
    │   └── …
    └── <app-name-B>/                  App B 的独立授权目录
        └── …
```

图中 `/` 只表示逻辑根，实际记录使用规范化的相对路径。module 表示模块身份，purpose 表示存储用途，app-name 表示平台为 App 登记并规范化的存储名称；该名称必须绑定由发布者公钥与 appId 验证出的稳定应用身份，不允许调用方任意指定。身份验证规则应复用现有机制。

每个内置插件的持久业务数据统一归入其声明的模块目录，文件、JSON、K-V 和 snapshot 不得各自形成分散的业务根。同一模块有多个用途时，在模块目录内使用用途子目录。系统保留区只存平台元数据和系统管理记录；不得再把一份插件业务数据分拆在模块目录和 `.keymaster/modules/` 两处。

目录名称采用稳定模块 ID，例如 `contacts/` 在界面显示为“联系人”；不因语言或插件显示名称变化而改路径。上面的联系人文件名仅为示意，正式文件名需采用稳定业务 ID，不能依赖可修改的姓名或列表顺序。JSON 数据按业务实体独立成文件，二进制内容按其业务格式存放，不要求转为 JSON。

`key.json` 的内容仍是加密 KeyHold JSON，文件扩展名不改变密码学格式；禁止保存明文私钥。导出文件名可以沿用现有 KeyHold 约定。

| 原结构 | 新结构 |
| --- | --- |
| IndexedDB 对象主键 `[bucketId, path]` | 对象主键 `path` |
| `keys/<公钥>.keyhold` | `key.json` |
| `<owner>/<module>/<purpose>/…` | `<module>/<purpose>/…` |
| `<owner>/.keymaster/modules/<module>/<purpose>/…` | `<module>/<purpose>/…`，统一归入模块目录 |
| `.keymaster/system/<module>/<purpose>/…` | 保留系统路径含义，取消桶绑定 |
| `<owner>/app.<publisher>/…` | 归入身份绑定的 `apps/<app-name>/…`，按 App name 分隔目录与权限 |
| `<owner>/lock.json` | 删除远程 Key 租约文件，使用本地运行互斥 |

App 管理设置与 App 自有数据须分开授权：App 不能通过文件权限修改 Keymaster 的授权、额度或其它 App 的记录。发布者公钥相同而 appId 不同的 App 默认隔离。若现有设置属于发布者级共享设置，应明确保留为平台管理记录，不能随目录变更复制成互相冲突的多份真值。

### apps 下按 name 隔离权限

每个 App 获得预绑定到 `apps/<app-name>/` 的独立存储句柄，读取、写入、删除、列举和批量提交都只能作用于该目录内。App 不能列举 `apps/` 根或其它 App 的内容，不能指定另一个 name 切换目录，也不能通过 `..`、绝对路径、编码绕过或相似目录前缀越界。

授权记录同时绑定验证后的 App 身份、登记的存储 name、允许操作和当前会话世代。name 用于目录划分，验证身份用于确认谁有权访问；仅有相同显示名称不能获得同一目录的权限。平台管理的授权设置仍不对 App 开放写入。

存储 name 在首次登记后保持稳定，显示名称修改或本地化不自动移动目录或转移授权。不同验证身份申请相同 name 时必须拒绝冲突，或由平台分配带稳定身份后缀的独立 name，绝不能共用目录。名称规范化和冲突分配的具体规则由后续契约设计确定。

撤销某个 App 的授权只使该 App 的句柄失效；删除其数据也只作用于其独立目录。目录之间的共享须通过平台显式授权的业务能力完成，不能直接开放另一个 App 的目录。

业务内容中的 ownerPublicKeyHex、签名公钥、收款身份等字段不能机械删除；它们仍可用于证据与身份核对。删除的是多 Key 的物理目录前缀和调用方选择 owner 的能力。

## IndexedDB 数据模型

使用独立的新数据库格式；建议生产数据库名为 `keymaster.wallet`，与旧 `keymaster.local` 分离，避免新结构误读旧复合主键。具体名称不是业务 API。

建议保留一个 `objects` 对象仓库，以规范化相对路径为主键；对象记录保存字节、大小、修改时间与版本。KeyHold、文件、K-V 和 snapshot 共用同一事务域，方便初始化、批量提交与重置原子完成。

必须满足：

- 唯一 Key 是结构约束：固定路径之外不能创建第二个 KeyHold；并发初始化只能有一个事务成功。
- 条件创建、版本比较和写入在同一个 IndexedDB 事务中完成，不能先读后在另一事务无条件覆盖。
- 业务提交以事务完成事件为成功依据，单个 request 成功不代表持久提交成功。
- K-V 批量 commit 与 snapshot 条件替换继续具有原子性和冲突检测。
- 文件读写、删除、分页列表及现有上层依赖的 Range/流式读取能力保留；分页不得默认全量读取全部对象字节。
- IndexedDB 使用本地事务一致性，不再为本地提交模拟网络超时、远程未知结果或 S3 ETag。
- 若现有接口需要版本标签，可以保留抽象版本标识；具体 revision/ETag 设计不得削弱并发检测，内容哈希不能替代全部运行世代校验。
- 原有对象式 K-V heads/values 是否改为原生记录，是后续技术设计选择；内部实现记录必须归属于对应模块/用途，不能破坏对外目录结构，也不能复制出第二份业务真值。不要求保留 S3 布局。

持久数据继续按 module、purpose、schema 和 authority 声明。每项声明须说明权威来源、保留条件和恢复方式；可重建数据按业务需求决定是否缓存，不能因为采用 IndexedDB 就把全部运行态落盘。

## 权限与生命周期

物理数据不再按桶和 Owner 隔离，但权限必须继续隔离。系统管理数据、内置模块数据和第三方 App 数据只能通过各自绑定的句柄访问，禁止插件自报路径、module、purpose 或目标身份以扩大权限。

取消 bucketId、bucketGeneration 和 activeKey 选择字段。句柄改为绑定当前唯一身份、会话 epoch、Worker 运行世代和钱包身份世代；字段命名由后续契约设计确定。

钱包身份世代是重置/重新初始化后改变的持久标识，不是可切换的第二个存储空间。它必须防止重置前的异步结果写入重新创建的钱包，即使重新导入的是同一把私钥，也必须视为新的授权生命周期。

锁定、重置、插件停用、App 撤权和 Worker 重启后，相关旧句柄及迟到结果失效。正常启动不得从持久记录恢复旧运行 grant、锁或解锁状态。持久 Connect 授权记录可以保留恢复决策，但活跃会话需重新建立运行绑定。

同一浏览器的多个 Tab 共享唯一 Coordinator 状态；解锁、锁定、改密和重置向各 Tab 发布事件。并发改密、初始化和重置必须由运行互斥与 IndexedDB 事务共同约束，不能只依赖页面按钮禁用。

删除原跨浏览器 Key 锁、持久锁心跳和租约续期体系。纯本地存储不承诺同一 Key 在不同浏览器之间互斥，也不承诺跨浏览器同步；跨设备业务安全要求由具体链上或服务端协议另行保证。

## S3 体系移除范围

彻底移除以下能力及其专用契约、配置、UI、依赖和测试：

- S3 / R2 / S3-compatible Provider、客户端工厂、AWS/Smithy 专用依赖及凭据处理。
- endpoint、region、bucket、access key、secret、CORS 配置与远程能力探测。
- 桶目录、桶管理、切桶组件、连接向导、远程不可用守卫及远程 bootstrap/device 配置。
- remote root manifest、远程初始化事务、远程认证/发现、S3 条件写降级和远程健康状态。
- S3 multipart 上传、分片清理、续传记录和 S3 专用资源测试/环境配置。
- 多 Key 仓储 list/readAll、Key 目录扫描、Key 切换和多 Key 初始化/恢复逻辑。

删除依赖前核对其它模块是否使用；仅移除属于本存储体系的用途。

网络业务继续存在。MSFile、BitFS、SatSubscription、WOC、消息与其它服务的文件传输、付费记录及结果未知恢复机制不能因名称包含 upload、remote 或 multipart 就一起删除。S3 上传能力移除后，现有调用方需要本地文件写入或业务服务上传的，分别绑定明确的新能力，不能留下无效 API。

## 旧数据与格式升级

本次不迁移旧数据。新版本不读取旧 catalog、device/session 桶配置或旧 IndexedDB 业务对象，也不据此选择钱包身份。

旧数据不因新版首次启动而自动删除。新钱包重置仅清空新格式数据；如产品另设“清理旧版本数据”，必须是独立、明确的删除操作。

使用新版后的本地 schema 升级与此次旧桶迁移是不同问题。后续仍须支持新格式版本校验、升级互斥和失败处理；版本过新或升级受阻不能退回创建空钱包。

加密 KeyHold 导出保留。完整钱包业务数据备份/恢复是否纳入本次范围待确认；在未纳入前，不应把 KeyHold 导出描述为完整钱包备份。

## 验收条件

1. 新环境从创建或导入直接得到唯一钱包，界面没有桶、S3 配置、Key 列表或切换入口。
2. 并发创建或导入只能产生一个完整钱包；事务失败不留下可用半成品。
3. 刷新、Worker 重启及浏览器重开后可读取唯一 Key 和持久数据，重新进入锁定状态。
4. 对象主键和业务根目录不包含 bucketId 或钱包 Owner 前缀，KeyHold 使用唯一固定路径。
5. IndexedDB 的文件、K-V、snapshot、条件写与批量提交行为可用，配额/不可用/版本错误明确。
6. 锁定、改密、重置和撤权的多 Tab 状态一致；失效句柄与迟到写入不能继续修改数据。
7. 重新导入同一私钥后，重置前的任务、grant 和 Connect 运行绑定仍不能恢复有效。
8. 第三方 App 与内置模块只能访问授权目录；同一发布者的不同 App 默认隔离。
9. S3 专用运行代码、契约、配置、依赖、资源测试及旧远程目标文档全部清除或改写；生产构建不含对应客户端。
10. 旧数据不会被读取、迁移或启动时自动删除；网络业务自己的恢复证据与传输能力正常保留。
11. 所有插件持久 I/O 只通过统一存储接口；静态边界检查禁止插件直接打开 IndexedDB 或使用其它持久化后端。
12. 根目录只有唯一 `key.json` 和声明的系统/模块/App 目录；联系人逐文件存放于 `contacts/`，P2PKH 数据归入 `p2pkh/`，同一模块的业务数据不会散落于多个根。
13. `apps/` 下按 App name 分目录和权限；跨 name 读写、目录列举和路径绕过均被拒绝。同名不同身份不会共享数据，显示名称变更不会改变授权归属，单 App 撤权或清理不影响其它 App。
