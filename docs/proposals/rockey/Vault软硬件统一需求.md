## 1. 已确认要求与建议边界

已确认：Vault 是统一的身份、会话、授权与撤权服务；软件 Worker 和 ESP32 硬件是两种密钥后端。每个 Keymaster 钱包只使用一个身份 Key、一个活动后端。原软件钱包迁入硬件后公钥和业务数据继续使用。硬件通过 USB 与浏览器通信，由三实体按钮独立解锁。硬件只执行可解释的白名单操作，支持本次允许、本次拒绝、会话持续允许、会话持续否决，并可在设备上取消持续决定。信用业务长文由 Keymaster 展示；硬件基础摘要可滚动，确认和否决始终可达。多语言字体选择性编译，预置免费开源字体及构建预设。

建议基线：硬件不保留旧软件密钥封装和旧密码解密入口，主动迁回软件时重新封装；用户对此倾向不保留，但尚未最终确认。八位数字 PIN、具体 M5Stack 型号、字体字号和容量限额均是待实测建议，不写成已确认参数。迁回软件、备份与设备擦除策略在实施相应功能前冻结。

## 2. 现状与目标架构

当前 `packages/contracts/src/vault.ts` 已有单 Key、钱包世代和会话失效规则，但解锁、密码验证、appView 建会话仍绑定密码。`activeKeyCrypto.ts` 主要提供摘要签名；P2PKH 在主机计算摘要。`workerKeySession.ts` 内 Channel 签名/加解密及本地秘密 HKDF 直接使用 Worker 私钥。`walletKeyRepository.ts` 将固定 `key.json` 解析为软件 KeyHold。以上均须适配，不能仅给 signDigest 增加 USB 转发。

```text
业务插件 / Connect App
           │
           ▼
Vault 统一服务：身份、会话、授权、撤权
           │
     ┌─────┴─────┐
     ▼           ▼
软件密钥后端            Rockey 密钥后端
既有检查通过后 Worker执行  设备核验、基础显示、物理确认、执行
```

业务插件依赖统一的操作能力，不依赖设备品牌、USB 句柄、密码或私钥。Vault 保留产品入口，设备适配器是内部后端。Coordinator 保持浏览器中的唯一权限与存储权威；设备对每次硬件执行独立判断。主机授权和设备授权均通过才可执行，浏览器不能扩大设备授权。

## 3. 单 Key、存储与注销

身份真值是压缩 `publicKeyHex`（公钥）；保管方式为 software 或 hardware。设备绑定标识不替代公钥身份，同型号设备、相同 USB 标识不证明持有当前 Key。

| 操作 | 数据行为 |
| --- | --- |
| 同一 Key 软件迁硬件或硬件迁软件 | 保留业务数据，替换保管方式，撤销全部旧运行句柄 |
| 同一 Key 重连或恢复设备 | 保留数据，新建会话并证明 Key 持有权 |
| 不同 Key 创建、导入或绑定 | 必须先注销并清除旧钱包数据 |
| 插入不匹配设备 | 明确拒绝，不自动切换、不自动注销 |
| 注销后再次导入同一 Key | 新钱包世代，不能复活旧授权和迟到任务 |

`key.json` 的后续格式须版本化：软件模式含软件密钥封装；硬件模式只含公钥、后端类型和公开绑定元数据。旧软件 KeyHold 可读取升级，不可因解析新格式失败自动创建空钱包。硬件模式不能偷偷保留软件密钥副本作为 fallback。

注销指清除当前格式钱包中的密钥记录、模块/App 数据、授权、日志与待执行任务；同时清除内存及持久恢复入口，跨 Tab 失效后才允许初始化另一 Key。范围以 `docs/存储.md` 的当前格式为准，不扩大到浏览器其它 Origin、链上数据、远端服务或用户已导出的备份。注销不是普通锁定或 Connect logout，也不自动擦除设备。设备擦除须单独物理确认。浏览器删除只能承诺逻辑清除，不承诺介质取证不可恢复。

同 Key 后端迁移保留钱包身份世代，推进会话及后端绑定世代；注销改变钱包身份世代。最终字段名由协议/存储 Gate 冻结。

## 4. 兼容的操作能力

| 能力 | 共同语义及硬件要求 |
| --- | --- |
| 身份、公钥和地址 | 核对持有权；地址按当前公钥和业务网络派生 |
| 身份证明、意图签名 | 核验用途、挑战、对象、权限和防重放上下文 |
| BSV P2PKH 签名 | 解析交易与前序输出证据，自算 sighash；硬件显示收款、找零、费用、网络与覆盖范围 |
| 费用池交易签名 | 独立核验已冻结阶段、脚本、双方/池对象、金额和锁定/退款条件；未冻结变体明确不支持，不能当普通 P2PKH |
| Channel 公共消息、Hash 请求、私密消息 | 支持现有编码、签名和封装；授权按协议、方向、对象和会话约束 |
| 本地秘密 seal/open | 保持现有 v3 密文、HKDF 和 AAD 兼容；私钥及长期派生密钥不返回业务插件 |
| 文件摘要签名 | 单独类型，明确摘要由主机计算；不能伪装成设备已读完整文件 |
| 会话撤权 | App、插件、连接、设备和钱包生命周期分别约束 |

能力需声明版本与支持的具体协议。Token、藏品、BitFS 专款/多签、订阅支付及未来自定义协议逐类接入解析器，未接入时显式不可用。不能以通用 signDigest 绕过硬件白名单，也不能退回软件后端。软件内部可保留摘要密码学原语，但业务授权入口表达可核验操作。

P2PKH 现有准备/费用求解阶段会尝试签名。目标必须先构建稳定未签交易与预览，再由设备确认签署；不能为了估费反复要求用户授权或产生可广播签名。必要的重建必须作废旧请求并重新确认，不能改变输出后复用批准。

兼容指验签、解封及协议结果兼容，不默认要求随机签名字节或随机密文字节完全一致。精确编码及确定性向量另行规定。

## 5. 解锁、会话与授权

设备 PIN 只在设备输入，USB 无代输或模拟按键入口。硬件解锁只允许设备使用私钥，不授予所有业务权限。统一服务不能要求硬件提交浏览器密码；软件仍可使用现有密码验证，硬件使用有作用域的设备授权证明。appView/Connect 会话不复用 Keymaster 的广泛授权。

区分设备连接、设备解锁、钱包会话可用、具体操作授权四种状态。现有 unlocked 的含义须改为“统一后端会话可用”，不能继续保证私钥在 Worker 内存。公开钱包元数据读取不等于业务存储或签名权限。

持续决定仅对匹配的会话和范围有效：

| 决定 | 当前与后续请求 |
| --- | --- |
| 未决定 | 设备询问 |
| 本次允许 | 执行当前不可变请求；随后仍未决定 |
| 本次拒绝 | 拒绝当前请求；随后仍未决定 |
| 会话允许 | 后续逐次检查范围、预算/次数等限制后执行 |
| 会话否决 | 后续直接拒绝，不重复弹窗 |

设备取消持续允许或持续否决后回到未决定，下次再询问。Channel 授权不包含支付、其他对象/协议、私钥导出或任意摘要。付款使用单独预算和白名单。允许与否决按具体操作范围匹配，不把一个 App 的决定用于另一个 App。

锁定、断线/连接失活、设备重启、Worker 重启、注销、后端迁移及 App 退出/撤权使相应旧句柄失效。设备执行前、浏览器交付结果前、最终存储/广播前各自复核有效性。设备取消授权同时取消尚未执行的匹配队列请求；已产生或交付的签名无法收回。设备内部授权撤销是权威，主机事件丢失也不能继续签。

软件不增加设备式逐笔批准；支付在已有检查及渠道单笔/App 会话累计额度内直接执行，超额才弹出一次批准，可提高本会话累计额度。软件已解锁不代表任意调用者已获权。

软硬模式均不自动重放结果未知的签名、迁移或支付请求。网络广播与硬件签名状态分别记录；签名成功不代表已广播。

## 7. 迁移与恢复

软迁硬：锁住新的业务任务 → 旧软件密码解锁 → 设备主动进入导入并设置 PIN → 人工核对配对码后建立认证加密通道 → 传输原 Key → 设备原子保存封装 → 公钥持有权、签名、旧消息及本地秘密兼容检查 → 条件提交硬件绑定并移除软件封装 → 清理软件内存并撤销全部旧会话。

USB 无法与 IndexedDB 形成一个原子事务，必须有迁移 ID（迁移标识）、公开 journal（恢复进度）和可查询的设备提交状态。设备已保存而浏览器未提交时仍使用原软件记录恢复/续作，不启动第二个活动后端；浏览器提交后不得默默回退软件。任何断电点不能先删除唯一可恢复副本。兼容验证不把真实秘密写入日志或报告。

硬迁软的冻结方案（2026-10-10 用户确认）：设备菜单主动进入导出 → 重新验证 PIN → 长按确认“私钥将进入软件环境” → 一次性认证加密传输到专用 Worker → 用新软件密码生成 KeyHold → 验证公钥及解封 → 浏览器原子保存新密码封装、付款账本与迁移阶段 → 用户在硬件上独立确认擦除旧私钥 → 校验擦除结果并结束迁移 → 启用软件后端。该操作不能持续授权，不能开放给 Connect。浏览器提交成功之前不能擦除硬件唯一副本；擦除失败或响应丢失时保留待恢复阶段，不能假报完成，也不能自动重新启用硬件后端。硬件删除由本次独立实体确认触发，普通 App、浏览器注销和软件提交不会自动擦除设备。

保留相同业务私钥及当前 Channel/HKDF 规则；设备专属保护密钥不能替代旧秘密的派生来源。Key 备份与完整业务数据库备份是两种独立备份。迁移不会使过去的软件副本或已导出备份消失。设备恢复材料必须保留准确的原单私钥，不假定它是 BIP32/BIP39 钱包根。

## 8. USB 与多页面

目标为浏览器直连 USB。三按钮 BASIC/FIRE 的具体型号未定；BASIC v2.7 的 USB 转串口建议使用 Web Serial，ESP32-S3 原生 USB 可另设传输适配器。应用协议与传输分离，不把 WebHID/FIDO 能力假设在 BASIC 上。

协议采用共同设计 §2 的最简模型：一个版本一个固定安全套件，操作能力/版本仍声明；握手后 REQUEST/RESPONSE/EVENT，控制使用操作名，无独立业务 ACK。设备单活动业务请求，主机有界排队，控制可达；当前/最近结果与单调接受水位防重放，老结果未知不自动重试。保留配对、持有权、会话隔离、长度/必要分片及撤权；内部世代不因 wire 简化删除。设备仅允许一个当前配对的活动控制连接；Keymaster 多 Tab 通过唯一 Coordinator 仲裁连接桥，不让每个 Tab 独立持有设备或复活 grant。控制页面关闭、串口丢失/被占用、后台失活分别呈现。实际浏览器 API 执行环境在 Gate 0 确认。

带电池设备不能以 USB 拔出当作断电。主机和设备通过失活检测撤销会话并锁定；具体检测机制与超时在协议 Gate 冻结。无可信时钟时，授权优先用连接、次数和预算限制，不凭主机时钟承诺安全期限。

## 9. 分期与验收

第一阶段必须覆盖单 Key、USB、设备解锁、同 Key 迁入、身份/意图、BSV P2PKH、Channel、v3 本地秘密、撤权及基础审核 UX。按能力发布进度，但全部门禁通过前不能宣称“完全替代软件 Vault”。迁回、备份也需独立验收，未实施时明确不可用。FIDO、独立 Lab 密钥、复杂资产解析和完整征信业务作为后续扩展；信用查询与 Markdown 归 Keymaster，不纳入硬件或 VLP；正式 Key 无盲签入口。

| 验收 ID | 必须证明 |
| --- | --- |
| KM-RK-01 | 软件原有路径可用；业务插件不获得 USB、PIN 或 raw Key |
| KM-RK-02 | 同 Key 迁入后公钥、消息解封、本地秘密、模块/App 数据可继续使用 |
| KM-RK-03 | 不同 Key 拒绝绑定；注销清空当前数据，旧句柄/迟到写入失效 |
| KM-RK-04 | 本次/会话允许与否决及设备取消决定正确隔离 |
| KM-RK-05 | 转账预览不签名；设备自算实际签名对象，换输出/找零/费用被检测 |
| KM-RK-06 | 基础摘要阅读位置、菜单默认项、重大警告和完整公钥符合要求 |
| KM-RK-07 | 多 Tab、断线、锁定、重启、撤权和结果未知不重复执行 |

### 硬件公开记录的实施约束（2026-10-10）

唯一固定路径 `key.json` 保持。软件继续使用原 KeyHold；硬件采用 `keymaster.hardware-key` v1，仅保存公钥、标签、钱包世代、非零 uint32 后端世代，以及 vaultlink / wireVersion 2 标识。不得混入软件密文副本、PIN 或私钥。格式和曲线点校验、与 meta 的世代比对只能证明本地记录完整，不能代替设备持有权挑战。硬件记录不得通过软件 KeyHold 导入、密码解锁或软件导出入口使用；设备绑定和同 Key 迁移须通过独立认证与原子提交流程。
