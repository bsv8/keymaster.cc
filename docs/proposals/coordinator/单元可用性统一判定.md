# 单元可用性统一判定

> 状态：需求已对齐，实施未完成。本文只记录已冻结的设计决策；迁移步骤见
> [施工单](../../../施工单/2026-09-21/005-单元可用性统一判定.md)。
>
> 相关真值：运行单元与作用域语义以 [插件生命周期](../../插件生命周期.md) 为准；
> 单元快照字段以 `packages/contracts/src/` 的中文注释为准。

## 1. 要解决的问题

### 1.1 事故

MSFile 卖方开关依赖 SatSubscription 运行时，但这个依赖只写在调用代码的一行 `await` 里，
没有任何声明位置。收款运行时预热未完成时，该调用抛错，异常被当成**永久配置错误**处理：
拆掉刚建好的卖方索引与运行时，状态标记为 `configuration-error`。

用户可见后果：解锁后立刻打开卖方开关，若收款运行时仍在预热，卖方会停在坏掉状态，
**必须手动再切一次开关**才能恢复。

### 1.2 同一状况在代码里有两种相反处理

解锁路径启动收款运行时时用 `void`（不等待）并只在失败时记一行日志，注释明确认定
「刚解锁还没就绪是正常的，先 defer」。卖方路径把同一状况判为致命。**这不是设计取舍，
是遗漏。**

### 1.3 根因

「A 需要 B 就绪」这个事实只存在于调用代码里。谁调、调在哪、B 何时会好，全靠调用方现场
推断，推断错一次就是一个竞态。

同时，「还没好」与「永远不会好」在类型上没有区别。真正对外的可用性判定返回的是
`string | undefined`，取值形如 `plugin-disabled:X`、`owner-session-unavailable`，
**瞬时与永久被压平成同一种字符串**。调用方无从区分，只能各自猜反应。

### 1.4 现状是两条并行的路径

| 路径 | 位置 | 问题 |
| --- | --- | --- |
| 框架门 | 单元可用性回调，框架据此置 `blocked` 或放行 | 有理由即置 `blocked` 并返回，不重试 |
| Worker 本地 | 4 个 `ensure*Runtime()` 函数，37 个调用点 | 各自手写同样的检查与兜底，不经过框架门 |

同一个单元，框架认为「可启动」，本地函数认为「没就绪」——**两把尺子**。本地函数还带一个
框架门不知道的测试逃生口，使分歧无法被门发现。

## 2. 可用性的定义

可用 = **插件开着 且 单元已就绪**，两者缺一即不可用。

| 插件 | 单元 | 可用 |
| --- | --- | --- |
| 开 | 已就绪 | 可用 |
| 开 | 未就绪 | 不可用 |
| 关 | 任意 | 不可用 |

两条推论：

- 读一个单元的「已就绪」就等于把该单元这条 AND 整条求过值了。已就绪的含义即
  「我插件开着 + 我依赖的全可用 + 我已就绪」。
- 没有单元的产品，其单元条件恒真，可用性退化为只看插件开关。**没有依赖要等就是永远
  可用**，这是判定规则的自然结果，不需要特判。

判定递归通过依赖图自然完成，调用方不自己递归。

## 3. 状态与原因

### 3.1 状态二值化

单元快照状态收敛为 `ready | failed`，**移除 `starting`**。

理由：`starting` 对消费者是废信息——收到了也不能用，等于没有。

### 3.2 failed 不是终态

`failed` 表示「现在不可用」，不表示「永远不会可用」。依赖变化后必须能自己变回 `ready`，
**不允许要求用户再操作一次**。这条是本设计的核心目的。

### 3.3 原因逐条列出

多依赖可能同时不满足，原因必须逐条列出并支持依赖链下钻，**不允许只报第一个**。
单元的 `failed` 原因就是第 2 节那条 AND 的失败分解。

### 3.4 诊断与状态分离

状态字段只回答「能不能用」。为什么不能，是 `reasons` 的职责。二者分离，界面才能把
「依赖未就绪」和「依赖已禁用」区分显示。

## 4. 依赖声明

单元目录的依赖字段合并为一份，容纳产品 id 与其它单元 id，统一按「是否可用」判定。
原有的「产品级运行前置条件」不再是独立一层。

- 启动时静态校验依赖图无环、无未知 id。
- 有任务的单元必须把自己产品写进依赖清单，沿用现有校验。
- 进了目录的单元必有任务或服务，沿用现有校验；因此「永远可用」不需要额外规则。

## 5. 触发方式

### 5.1 回调，不是轮询

Worker 进程内提供可用性订阅，签名沿用仓库既有惯例 `onChange(handler): () => void`，
返回取消函数。可用性变化时 **`ready` 与 `failed` 都触发**，不是只在变好时通知。
消费方订阅后重判自身状态，重判必须幂等。

**任何环节不得引入轮询、等待休眠或超时猜测。** 抖动只会带来连续几次幂等重判。

### 5.2 页面侧通道已具备

页面侧沿用既有的 `worker.units` 推式通道与其单调修订号，不新增轮询。本次唯一需要新增的
机制是 Worker 进程内订阅。

## 6. 单一路径

这是本设计的硬约束，优先级高于任何便利性考虑。

- 各 `ensure*Runtime()` 中的「reconcile 一下然后祈祷它已就绪」兜底**全部删除**。
- 框架门与 Worker 本地判定**合并为同一实现**，不允许各判一次。
- 门外的测试逃生口**取消**；测试改用既有公开测试钩子表达同样场景。
- **不保留双轨、不做分阶段灰度、不留迁移中间态提交。** 切换即切换。

统一比渐进重要：两条路并存时，「哪条路是对的」本身就是一个需要反复判断的问题，
而这正是本次事故的成因。

## 7. 卖方开关的具体含义

用户开关与实际可接单状态是**两个正交维度**，不合并。

- 开关关 → 短路，不评估可用性，不残留索引与运行时。
- 开关开 → 评估可用性。不可用时如实报不可用并订阅变化，**不拆解、不要求用户重切**。
- 「依赖未就绪」不得再由永久错误状态表达。现有「自建索引中」与「协议端口未就绪」
  语义都不同，需要独立的一档状态，避免界面提示错位。

## 8. 字段

| 字段 | 中文含义 |
| --- | --- |
| `code` | 不可用的稳定代码，程序据此判断、测试据此断言 |
| `dependencyId` | 不可用的依赖：产品 id 或单元 id |
| `text` | 界面直接可用的文案，含翻译 key 与**英文**兜底；中文走 i18n 资源 |
| `dependsOn` | 本单元可用所依赖的全部对象 |
| `state` | `ready` 或 `failed` |
| `reasons` | 失败原因的全部分解；`ready` 时为空 |

`text` 沿用 `packages/contracts/src/i18n.ts` 既有的 `I18nText`，与既有 `blocked` 状态
同一套文案体系。**兜底文案一律英文**，与仓库现有默认语言一致。

## 9. 本提案不包含

1. 不改 `webloom-framework` 的对外 API。框架内部状态与本文状态之间的翻译在 Keymaster
   侧集中完成，不散落。
2. 不做依赖关系的可视化界面。
3. 不改各业务单元内部的启动实现，只统一「能不能用」的判定与触发。
4. 不改变单元依赖的业务含义（哪些单元依赖哪些产品），只改声明形态。
