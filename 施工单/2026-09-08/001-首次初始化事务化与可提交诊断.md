## 1. 背景与问题

当前首次初始化向导在第 3 步“设置密码”点击“保存并继续”时，已经执行首桶创建、Hold 快照写入、目录选择和 Storage 解锁；第 4 步的 Key 类型、Key 标签或导入材料尚未收集。

这会制造一个产品不允许的中间状态：

```text
已存在选中的桶和空 Hold 快照
  + 尚无第一把 Key
  + Vault/应用装配可能尚未完成
  + 刷新后只能识别为“有桶但初始化未完成”
```

已观察到的错误包括：

- `No selected storage bucket`；
- `Local storage bridge lease is invalid`；
- 初始化完成后因资源装配竞态进入 Fatal 页面，例如 `Resource definition "storage.status" not found`。

现有 `e2e/initial-setup.spec.ts` 虽覆盖部分页面操作，但没有把“最终提交前零持久化、失败后完整回滚、刷新后无半截状态、成功后重载可用”固定为发布门禁。

## 2. 目标

首次初始化改为一个明确的、可恢复的业务事务：

```text
步骤 1～4：只收集和校验内存草稿
  -> 最终确认
  -> 预检完整计划
  -> 暂存不可见数据
  -> 一次提交权威引用
  -> 安装 Storage/Vault/active Key 运行态

任一步失败
  -> 撤销本次权威提交
  -> 清理本次可识别的暂存数据
  -> 回到初始化前状态
  -> 保留可安全重试的表单草稿
```

交付同时包含：

1. Local 与 S3 共用的初始化事务契约；
2. 完整 Playwright 冒烟与失败注入测试；
3. 面向用户的可行动错误摘要；
4. 可展开、可复制、经过脱敏的技术诊断；
5. Fatal 页面使用同一套脱敏与复制规范。

## 3. 冻结的不变量

### 3.1 最终确认前不得持久化业务状态

- [ ] 选择桶类型、填写参数、设置密码、选择 Key 类型、填写 Key 标签、解析导入材料，都只更新当前页面内存草稿。
- [ ] 第 3 步不得调用 `prepareBucketConfig`、`unlockBucket`、Vault 创建、目录写入或业务 K-V 写入。
- [ ] 第 4 步资料未完整时不得创建空桶、空 Vault、空 Key 索引或 selected bucket。
- [ ] 刷新、关闭标签页或点击返回只丢弃内存草稿；重新进入时仍是未初始化状态。
- [ ] S3/Local 参数探测允许使用可证明已清理的临时探针对象，但不得写入正式目录、Hold 提交头、Vault 或应用 K-V。
- [ ] 密码、S3 Secret Access Key、Session Token、WIF、Hex 私钥和导入源密码不得进入 localStorage、sessionStorage、URL、日志、诊断文本或 React 外的长期缓存。

### 3.2 成功状态必须完整

最终提交成功时必须同时满足：

- [ ] 本机桶目录仅新增一个完整条目，且 `selectedBucketId` 指向该条目；
- [ ] 桶内存在已提交且认证有效的 Hold 快照；
- [ ] Hold 快照包含连接配置和恰好一把首 Key，不允许先提交空 Key 集合；
- [ ] Vault verifier、公开 Key 索引、Coordinator selected key 与 Hold 快照一致；
- [ ] 第一把 Key 已成为 active key，Vault 状态为 `unlocked`；
- [ ] Storage/Vault/Keyspace 能力均可用，进入 Key 管理页不会出现资源定义缺失的瞬时 Fatal；
- [ ] 刷新页面后使用同一桶密码可以恢复同一 Key，不能依赖初始化页面残留内存。

### 3.3 失败状态必须回到事务前

最终提交任何阶段失败时：

- [ ] 权威桶目录恢复为事务开始前的精确版本；首次初始化场景应恢复为空目录且无 `selectedBucketId`；
- [ ] Vault meta、公开 Key 索引、Coordinator 选择及 owner namespace 不得留下本次记录；
- [ ] 已发布但尚未成为权威引用的 Hold/commit/value 必须不可达，启动逻辑不得识别；
- [ ] 能安全定位的本次暂存对象应立即删除；无法确认删除的对象进入有界 GC/恢复记录，不得谎报“已全部回滚”；
- [ ] Local 清理只能作用于本次生成的 `bucketId`；S3 清理只能作用于本次配置的受限前缀；
- [ ] 回滚失败必须升级为“初始化未完成，清理需要重试”的独立状态，不能覆盖原始失败，也不能显示初始化成功；
- [ ] 重复点击、响应丢失、页面超时和同一事务重试必须幂等，不得创建多个桶或多把首 Key。

## 4. 初始化计划与字段

最终步骤提交一个完整的内存计划，禁止由不同组件分别拼装持久化动作：

```ts
interface InitialSetupPlan {
  /** 本次初始化事务 ID；只用于幂等和回滚定位，不是桶身份。 */
  transactionId: string;
  /** 桶显示名称。 */
  bucketLabel: string;
  /** Local 或 S3 后端。 */
  backend: "local" | "s3";
  /** 尚未持久化的连接配置；S3 内含临时凭据。 */
  connection: StorageBucketConnectionConfigV1;
  /** 桶密码；只活在本次提交调用内。 */
  bucketPassword: string;
  /** 新建或导入的第一把 Key。 */
  firstKey: InitialSetupFirstKey;
}

type InitialSetupFirstKey =
  | {
      kind: "generate";
      /** Key 显示标签。 */
      label: string;
      /** 首 Key 默认能力，例如 p2pkh。 */
      capabilities: string[];
    }
  | {
      kind: "import";
      /** Key 显示标签。 */
      label: string;
      /** importer 已解析且通过格式校验的临时私钥材料。 */
      material: KeyImportMaterial;
      /** importer 识别出的格式。 */
      format: string;
      /** importer 身份，用于公开来源说明。 */
      source?: string;
      /** 首 Key 默认能力，例如 p2pkh。 */
      capabilities: string[];
    };
```

字段名称可以在实现时与现有 contracts 合并，但每个公开字段必须有中文说明，不得另建含义相同的平行类型。

## 5. 事务边界设计

### 5.1 单一高层入口

- [ ] 在 contracts 中增加单一高层初始化操作；页面不得继续按 `prepareBucketConfig -> unlockBucket -> createVaultWith...` 自行编排。
- [ ] 操作接收完整 `InitialSetupPlan`，先完成纯校验，再开始任何正式写入。
- [ ] 事务执行者必须拥有 Storage、Hold、Vault 与 Coordinator 状态的回滚知识；React 页面只接收进度、成功结果或结构化错误。
- [ ] 新建 Key 的随机私钥优先在受信任的 Worker/Vault 边界生成；若现有架构必须在 Window 暂存，需单独给出安全论证并在所有路径清零可控字节缓冲区。
- [ ] 导入私钥只在 importer 解析和事务提交之间短暂留在内存；成功、失败、返回、切换格式和组件卸载均清理。

### 5.2 推荐提交协议

实现应采用“暂存数据不可见、最后切换单一权威引用”的协议：

1. 读取并固定事务前目录版本；首次初始化必须确认没有现有桶/Vault；
2. 对完整计划执行字段、密码、连接、Key 格式和重复身份预检；
3. 生成稳定 `bucketId` 与 `transactionId`，在候选命名空间写入连接配置和首 Key 的完整 Hold 快照；
4. 验证刚写入的 Hold 文档、提交头、Key 公钥和配置均可用；
5. 初始化可由 Hold 重建的 Vault verifier/公开索引/Coordinator 元数据；
6. 通过一次目录 CAS 发布桶条目和 `selectedBucketId`，这是业务可见性的提交点；
7. 安装 Root、激活第一把 Key，并发布 ready/unlocked 状态；
8. 若第 6～7 步失败，执行补偿 CAS 和运行态撤销，恢复事务前状态；
9. 成功后清除密码、派生上下文、导入明文和事务暂存状态。

若底层对象存储无法提供跨目录和多 K-V 的物理 ACID，至少必须保证：

- 读者只承认最终权威引用可达的数据；
- 失败前的暂存对象永远不会被当作已初始化；
- 补偿和 GC 可按 `transactionId/bucketId` 精确定位；
- UI 不把“可恢复的完整提交”和“已经回滚的失败”混成同一状态。

### 5.3 并发、刷新与响应丢失

- [ ] 同一浏览器两个标签页同时初始化，目录 CAS 只能有一个成功；失败标签页回滚时不得删除成功标签页的数据。
- [ ] 最终提交中刷新/关闭页面，由 Worker 或恢复编排继续完成提交或回滚；不得依赖 React `finally` 才能保证一致性。
- [ ] 最终响应丢失后，使用同一 `transactionId` 查询结果；不能盲目重做生成 Key。
- [ ] SharedWorker 的 Local bridge lease、authority 和 bucket generation 必须在暂存及最终提交阶段分别校验，旧 `unselected` 事件不得覆盖候选租约。
- [ ] 事务恢复记录不得含密码、凭据或私钥，只保存公开 ID、阶段、版本和脱敏错误分类。

## 6. 向导改造

建议步骤：

```text
1. 桶类型
2. 桶参数
3. 桶密码
4. 第一把 Key
   - 新建：Key 标签
   - 导入：格式、材料、源密码、解析结果、Key 标签
5. 确认并初始化（最终提交点）
```

- [ ] 第 3 步主按钮改为“继续”，不得再使用暗示已持久化的“保存并继续”。
- [ ] 第 4 步完成前可返回修改桶参数和密码，不触发清理事务。
- [ ] 最终确认页以中文列出桶类型、显示名称、S3 脱敏位置、Key 类型、Key 标签；不回显密码或完整凭据。
- [ ] 最终按钮文案明确为“创建桶和第一把 Key”或等价表述。
- [ ] 提交期间显示稳定阶段，例如“正在验证”“正在写入完整快照”“正在完成初始化”“正在回滚”，但不得显示秘密或底层随机 ID。
- [ ] 失败后保留非敏感草稿；密码和私钥是否保留必须按错误阶段显式裁决，默认清除并要求重新输入。
- [ ] 刷新时不恢复内存草稿，也不自动继续未确认的初始化。

## 7. 用户错误与可复制诊断

### 7.1 两层错误模型

默认错误区只显示用户可以理解和行动的内容：

```ts
interface UserFacingError {
  /** 中文短标题，例如“无法完成初始化”。 */
  title: string;
  /** 说明哪一步失败及数据是否已回滚。 */
  summary: string;
  /** 用户下一步，例如“检查浏览器存储权限后重试”。 */
  action?: string;
  /** 稳定错误码，用于搜索和工单关联。 */
  code: string;
  /** 一次错误的公开关联 ID，不得等于秘密租约 ID。 */
  incidentId: string;
  /** 已脱敏、默认折叠的诊断文本。 */
  diagnostic: string;
}
```

- [ ] 不直接把 `Error.message` 作为唯一 UI 文案；Storage/Worker/DOM 英文异常必须映射为稳定中文摘要。
- [ ] 摘要必须明确结果：未写入、已回滚、回滚未完全确认、或已经完整提交但页面恢复失败。
- [ ] 技术详情使用 `<details>` 或等价可访问折叠区，默认关闭。
- [ ] 提供“复制诊断信息”按钮，复制成功/失败均有可访问状态反馈。
- [ ] Clipboard API 不可用时使用安全 fallback，失败不得再触发 Fatal。

### 7.2 脱敏规则

脱敏必须在生成 UI/Clipboard 文本前完成，而不是只靠 CSS 隐藏：

- [ ] 删除密码、导入源密码、Secret Access Key、Session Token、Authorization、Cookie 和签名；
- [ ] 删除 WIF、32 字节私钥、助记词形状及可疑长 token；
- [ ] URL 删除 userinfo、query、fragment；Endpoint 最多保留 scheme + host；
- [ ] Access Key ID、public key、bucket 物理名称、request/lease/session ID 按诊断需要截断或哈希，不复制完整值；
- [ ] JavaScript stack 保留错误类型、仓库相对模块和行列，删除本机绝对路径、浏览器用户目录、扩展 URL 和动态查询参数；
- [ ] 对象递归序列化必须有深度、条数和总长度上限；循环引用不得导致二次错误；
- [ ] `cause` 不允许未经筛选直接 `JSON.stringify` 后显示；
- [ ] 诊断文本标注应用版本、时间、阶段、稳定错误码、incident ID、回滚结果和脱敏版本。

脱敏函数必须是可单测的纯函数，由初始化错误区与 Fatal crash page 共用，禁止各写一套正则后逐渐漂移。

### 7.3 Fatal 页面

- [ ] `apps/web/src/fatalCrashPage.ts` 不再直接展示原始 `snapshot.message/stack`；先走统一脱敏器。
- [ ] 保留“刷新页面”，增加“复制脱敏诊断”；不得增加清空数据、导出私钥或绕过门禁操作。
- [ ] Fatal 渲染器自身失败时的 `<pre>` fallback 也只能包含脱敏文本。
- [ ] 重复渲染保持幂等，复制监听器不得叠加。

## 9. 自动化验证矩阵

### 9.1 Playwright 完整冒烟

以下测试使用真实生产构建、真实 SharedWorker 和浏览器 Local 存储桥，不得用页面 mock 替代：

| ID | 场景 | 通过标准 |
|---|---|---|
| E01 | Local + 新建 Key 完整初始化 | 从空浏览器走完所有步骤；进入 Key 管理；显示唯一 Key；刷新后仍可恢复 |
| E02 | Local + Hex 导入完整初始化 | 导入固定测试私钥；显示预期标签和公钥；刷新后不重复导入 |
| E03 | 步骤 1～4 分别刷新 | 每次刷新后目录、Hold、Vault、Key 索引均为空；重新进入从首步开始 |
| E04 | 第 4 步返回修改 | 不写数据；修改后最终只创建一桶一 Key |
| E05 | 最终提交重复点击 | 按钮防重入；只有一个事务、一个桶和一把 Key |
| E06 | 最终响应丢失后重试 | 查询同一事务结果，不生成第二把 Key |
| E07 | 两标签页并发初始化 | 仅一个提交成功；另一页友好提示且不删除成功数据 |
| E08 | 成功后应用装配 | 不出现 Fatal；`storage.status`、Vault、Keyspace 资源持续存在 |
| E09 | 友好错误与诊断复制 | 页面显示中文摘要；复制文本含错误码/阶段且不含注入的密码、凭据、私钥 |
| E10 | 回滚未确认 | 明确提示需要重试清理，不允许继续进入业务页面 |

Playwright 至少保留一个名为“首次初始化完整冒烟”的串行测试，完成：

```text
空 context
  -> Local
  -> 桶名称
  -> 密码
  -> 新建 Key + 标签
  -> 最终确认
  -> Key 管理显示该 Key
  -> reload
  -> 使用桶密码恢复
  -> 同一 Key 仍存在且可激活
```

测试必须断言页面没有 `[data-fatal-crash]`，并在关键步骤直接读取浏览器允许公开检查的目录元数据，证明最终确认前没有 selected bucket。测试结束使用全新 BrowserContext 隔离，不能依赖前一用例残留。

### 9.2 失败注入与回滚

对每个写入边界提供确定性失败注入，至少覆盖：

| ID | 注入点 | 回滚断言 |
|---|---|---|
| R01 | 连接配置加密/预检失败 | 零写入 |
| R02 | 首个 Hold value/commit/head 写失败 | 目录不出现候选桶；暂存不可达 |
| R03 | 目录 CAS 失败 | 原目录不变；不删除并发赢家数据 |
| R04 | Vault verifier 写失败 | 目录、Hold 权威引用和 Key 索引恢复 |
| R05 | 公开 Key 索引写失败 | 不留下可选桶或空 Vault |
| R06 | owner namespace 初始化失败 | 首 Key、meta、索引和目录全部回滚 |
| R07 | active Key/Coordinator meta 失败 | 不进入 unlocked；重启仍是事务前状态 |
| R08 | Local bridge lease/authority 变化 | 拒绝旧请求并安全回滚，不显示底层英文异常 |
| R09 | 回滚期间 Provider 删除失败 | 标记 rollback-unconfirmed；诊断含脱敏阶段，不谎报空状态 |
| R10 | 任意阶段页面刷新/Worker 重启 | 恢复编排完成提交或回滚，不留下半截权威数据 |

### 9.3 单元与集成测试

- [ ] 初始化 reducer/状态机证明步骤切换不调用任何持久化依赖；
- [ ] 高层事务成功、失败、补偿、幂等和并发 CAS 测试；
- [ ] Local 与 S3 Provider 暂存清理范围测试；
- [ ] Hold 文档包含恰好一把首 Key 的认证往返测试；
- [ ] 导入材料在成功/失败/取消后的清理测试；
- [ ] 错误映射和中文 fallback 测试；
- [ ] 脱敏器对密码、WIF、Hex 私钥、S3 凭据、URL、绝对路径、循环对象和超长 stack 的测试；
- [ ] Fatal 页复制诊断与 fallback 脱敏测试；
- [ ] React Resource 生命周期测试，防止初始化完成后短暂注销 `storage.status`。

### 14.4 2026-09-09 手工恢复清理 P0 修复与账本容量保护

复核发现清理重试在撤销目录后把原有 `error` 带入 `status: "pending"`，会被生产账本解析器拒绝，导致目录已撤销但候选对象永远无法删除。本轮已修复：

- Worker 测试桥接器复用生产恢复账本成员解析器；新增回归断言覆盖“真实账本校验下先撤销目录、再删除候选对象”，避免测试 mock 放宽状态约束。
